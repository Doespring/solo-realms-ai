# Проверка реестра патчей Nat20 (п.5 раунда 4/5)

Реестр: `vendor/nat20/PATCHES.json`, commit `e187c813bb4e43c4e4e62942ecd83831f1cdbcaa`,
upstream `https://github.com/tapestria/nat20`, версия `0.7.0`, 16 записей.

Проверялось **не по реестру**, а по байтам:

## 1. Байты совпадают с записанными хешами

Для каждой записи пересчитан SHA-256 фактического файла.

| проверка | результат |
|---|---|
| файлов в реестре | 16 |
| отсутствуют на диске | 0 |
| хеш совпадает | **16** |
| хеш расходится | **0** |

## 2. Реестр полон

Изменённых файлов в `vendor/nat20` по `git status`: **1672** (включая 1663 `.json` корпуса).
Изменённых `.py`/`.toml`: 7 — **все 7 присутствуют в реестре**, неучтённых нет.

## 3. Девять записей без изменений в git — не ошибка

`__init__.py`, `activities/mastery.py`, `build_party.py`, `build_spec.py`,
`orchestrator.py`, `rest.py`, `rules/advancement.py`, `specs.py`, `types/combat.py`
не показываются в `git status` как изменённые, потому что их правки **уже вошли в коммит
`6e3f094`** («Nat20: восстановление зарядов предметов и активностей по явным событиям»).
Реестр описывает отличие от upstream-эталона, а не от индекса git, поэтому такие записи
законны.

## Чего эта проверка не доказывает

Совпадение хешей доказывает, что реестр **описывает текущие байты**. Оно не доказывает,
что каждый патч корректен по правилам SRD 5.2 и что механика считает верно. Это отдельный
вопрос, и реестр на него не отвечает.
