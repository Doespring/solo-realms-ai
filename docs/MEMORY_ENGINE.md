# Memory Engine

Продолжена реализация Pass 1.7, существующий storage не заменён. Schema 6 добавляет memory_entities, memory_records, memory_access, memory_subjects и memory_fts. Game State и events остаются каноническими источниками. Запись содержит source event/ref, provenance, truth class, scope, локацию, игровое время, важность и разрешённых адресатов.

В одной транзакции Store.apply: правила → событие → состояние → проекция памяти. Idempotent event key не создаёт повторную запись. Intent/attempt/statement/rumour/belief отличаются от fact. Unsupported use не становится кражей или получением предмета. Отношение меняется только из подтверждённого structured state, не от красивой фразы Narrator. Шёпот адресату не получает автоматически каждый присутствующий.

NPC идентифицированы в пределах кампании; имена и алиасы — для поиска, ACL — по ID. Knowledge grants относятся к событию. Retrieval фильтрует по campaign, source event active/undone, as-of seq, scope и списку знающих субъектов. Secret/gm не сериализуются для Narrator. Между ветками/кампаниями отменённые знания не используются. При исторической перегенерации применяется снимок события, а не нынешний мир.

FTS5 и лёгкая нормализация русского дополняются сущностями, участниками, локацией, типом/важностью и давностью. Разумные группы синонимов не заменяют полной морфологии. Выбор ограничен по числу и символам; длинные воспоминания компактизируются до проверки бюджета. Scene Packet не содержит длинного журнала или произвольной старой прозы.

Store.record_scenario — trusted Python hook для авторского/программного источника, не публичный API и не функция, доступная LLM. Он не является готовым Inventory/World/Combat Engine. Полезен для достоверных fixtures и будущих зарегистрированных механик. Истинность импортированной авторской записи и правильность audience обязан обеспечивать доверенный импортёр. Проза может ошибиться в атрибуции; такие ошибки не создают знания в программной памяти.

## Стык механического движка, 17 октября 2026

Дополнение интеграции мастера: `Game.play_command` выбирает Nat20 для `state.nat20`
и прежний CommandEngine для остальных кампаний. Реальный backend сохраняет native

Контекст и повтор используют выбранный backend и общий memory-v1; внутренний
replay Nat20 при новом исполнении проверяет native read-model, как описано в

проверкой самого контракта; реальный HTTP-путь покрывает `test_nat20_command_cycle.py`.

Итоговый `../ReuseFirstAudit-2026-10-17/REUSE-FIRST-ARCHITECTURE-AUDIT.md` требует **Reuse Solo** для памяти и журнала. Существующие `Memory.put/ingest/retrieve`, FTS, сущности и ACL сохранены. Дополнительная таблица `memory_engine_events` связывает внешний ID с существующим событием Solo; второй журнал и новая система памяти не создаются. Таблица добавляется идемпотентным `CREATE TABLE IF NOT EXISTS` при открытии Store, без переписывания старых событий и кампаний.

Название **«Verskylight» не обнаружено**: проверены имена файлов и текст исходников/документации Solo Realms, включая варианты `versky` и `skylight`. Соответствие реальному компоненту установить нельзя. Фактические существующие компоненты памяти: `solo/memory.py:Memory`, `solo/storage.py:Store`, `solo/game.py:SceneCompiler`; называть какой-либо из них Verskylight оснований нет.

### Единственный временный контракт

`solo/engine_memory_contracts.py` содержит `GameEvent`, `GameSnapshot`, `pair()`. Версия — **memory-v1**, временный контракт стороны памяти, согласованный для этой задачи. Это **не окончательный API движка и не типы Nat20**. `GameCommand` здесь не определяется. Когда ветка движка станет доступна, согласовать/импортировать общие типы в этом одном стыке, не заводить параллельные события.

Вход `EngineMemoryAdapter.deliver(event, snapshot)` принимает DTO или словари. Он доступен только доверенному Python-коду; HTTP/LLM-инструментом не является. Само прохождение валидации не доказывает происхождение данных: получатель обязан вызывать этот метод только для результатов программного движка.

* GameEvent: `id`, `campaign_id`, `branch_id`, `sequence`, `parent_event_id`, `type`, типизированный `payload`, `subjects`, `known_by`, `scope`, `source_ref`, `game_minutes`.
* GameSnapshot: та же идентичность события/кампании/ветки/sequence, `location`, `actors`, `combat`. Для каждого actor и отдельно его HP, ресурса, состояния, позиции заданы `scope/known_by`; для combat они тоже явные. Субъекты и адресаты — стабильные ID, не поиск по похожему имени. ID героя — `hero`; ID NPC должен соответствовать каноническому `npc.id` (либо прежней identity для NPC без ID). Имена и UUID памяти не заменяют эти внешние ID.
* `pair()` отклоняет лишние поля, неизвестные типы/субъекты/адресатов, несовпадение идентичности и заявленного результата со снимком. `deliver()` проверяет parent/sequence относительно текущего снимка и `before` для HP, ресурсов и перемещения. Урон, итог броска и прочие значения уже рассчитаны движком; арифметики D&D в адаптере нет.

### Отображение событий

Каждое принятое одиночное механическое событие даёт одну запись существующей памяти с `truth=fact`, `provenance=confirmed_event`. Текст формируется только из проверенных полей payload. `scope`, адресаты, subjects, `source_ref` и игровое время переносятся без расширения доступа. Присутствие рядом с героем не делает NPC свидетелем автоматически; `public` также требует явного `known_by`.

Обновление общего `memory-v1` в рабочем дереве добавило `command_resolved`: это один envelope с типизированными `effects` для атомарной команды. Адаптер разворачивает каждый effect в отдельную запись прежней памяти, с ключом `engine:<id>:effect:<index>` и `source_ref.effects[index]`. `outcome` не является фактом, не индексируется и в контекст памяти не попадает. Команда без effects не создаёт записи памяти. У каждой записи сохраняются subjects envelope и подтверждённые target/participants конкретного effect; адресаты не расширяются. Проверка `pair()` сверяет конечные значения каждого изменённого поля со снимком и непрерывность нескольких effects одного поля; арифметика правил не выполняется.

| type / kind памяти | Подтверждённые поля payload |
|---|---|
| roll | kind check/save/attack/initiative, dice, total, success (может быть null) |
| damage / healing | target, amount, before, after HP |
| resource | target, resource, before, after |
| condition | target, condition, active (добавление/снятие) |
| movement | target, before/after координаты |
| combat_started / combat_ended | combat_id, participants; active проверяется по снимку |

Внешний `source_event`, `branch_id`, `sequence`, parent и подпись хранятся в `memory_engine_events`, внутренний `event_id` — прежняя ссылка на журнал Solo. Retrieval для механических записей возвращает оба ID, subjects, scope, branch, `as_of` и `engine_sequence`, дополнительно к прежним provenance/truth/source_ref. `as_of` — **seq журнала Solo**; он отличается от локальной `engine_sequence` и не является игровым временем.

Свободный текст мастера, `narrative` и произвольный `payload.text` контрактом не принимаются. Редактирование/регенерация прозы не создаёт фактов и прав доступа. Существующие statement/rumour/belief/intent/attempt продолжают обрабатываться прежним путём.

### Доставка, undo и восстановление

`deliver` использует существующий `Store.engine_event` и `BEGIN IMMEDIATE`: запись actions/events, полный переданный снимок в `state.engine_snapshot`, связь ID, запись памяти/FTS/ACL — одна транзакция. Ошибка проекции откатывает всё. Исходный envelope сохраняется внутри scripted results для воспроизводимой проекции; его и полный снимок удаляют существующие публичные проекции истории/SSE/кампании.

Повтор того же внешнего ID и нормализованного содержимого возвращает исходное событие, без смены состояния и новых воспоминаний. Под тем же ID другое содержимое отклоняется; ID уникален в кампании, включая ветки. Отменённая доставка не воскрешается повтором. После undo можно продолжить от восстановленного parent новым ID и **новым branch_id**. Пропуски sequence, будущие/чужие parent и повторное использование заброшенной ветки отклоняются.

Существующие undo/checkpoint/restore восстанавливают `engine_snapshot` вместе со всем state; активные знания определяет прежний `events.undone`. Унаследованные события предков сохраняют исходную ветку. В контекст не попадает неактивная соседняя ветка. Перезапуск читает SQLite и переданный снимок; вычислять механику или повторять броски для восстановления не требуется. Это проверяет устойчивость **стыка памяти**, а не восстановление внутреннего состояния Nat20, которое остаётся задачей ветки движка.

### Контекст мастера

`EngineMemoryAdapter.context(campaign, npc_id=None, query='', as_of=None, branch_id=None, limit=6, budget=6000)` также доступен через `SceneCompiler.engine_context`. Возвращает отфильтрованный текущий/исторический снимок механики, релевантные воспоминания и provenance, сведения о ветке/источнике. Для NPC передаётся его стабильный внешний `npc_id`; без него аудитория — герой. `npc_knowledge` содержит ID записей из `memories`, без повторной сериализации текста.

**Один пакет — одна аудитория.** Пакет NPC не получает воспоминания или личные ресурсы героя/другого NPC. `private` доступно только явному адресату, `secret/gm` исключается даже для владельца, как в прежнем SceneCompiler. Программный `Memory.knows` учитывает и секреты. Проверки scope/known_by применяются к каждому полю снимка; скрытая сущность и скрытый участник текущего хода не раскрываются. Снимок и retrieval читаются в одной SQLite read-транзакции, чтобы concurrent undo не смешал разные состояния мира.

`as_of` ограничивает активный путь истории; запрос неактивной ветки отклоняется. Исторический пакет берёт сохранённый на тот момент снимок, а не нынешнюю механику. Старые воспоминания Solo тоже доступны по существующему ACL и as-of. Сборщик не делает LLM-вызовов. Реальный Nat20 подключён к command-turn для явно выбранных кампаний; существующий UI и обычные кампании не переключаются на фикстуры.

## Проверка на реальном Nat20

Следующий ограниченный этап описан в [PLAYABLE_SCENE.md](PLAYABLE_SCENE.md):
`examples/lantern-post` использует прежний ScenarioPackage/Item и настоящий
Nat20GameEngine, включая восстановление активного боя в новом процессе.
`tests/test_playable_scene_memory.py` проверяет реальные native effects, их
источники, NPC ACL, повтор команд/награды, проза → отсутствие новых фактов,
undo/новую ветку/checkpoints и откат награды при сбое памяти.

Для этого этапа адаптер контекста поддерживает канонических социальных NPC,
отсутствующих в боевом снимке; HP/ресурсы им не придумываются. Сценарный evidence
сохраняет явный source_ref. При закрытии native боя память берёт ID закрытого
столкновения из проверенного CombatOutcome/closed_combat и предыдущего снимка,
поскольку текущий снимок уже имеет combat.id=none. Общие игровые маршруты и
ограничение на активный AdventureDefinition не меняются; точный недостающий стык
для интегратора приведён в документе сцены.
