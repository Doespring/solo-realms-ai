# Письмо у старого фонаря

## Windows preview.7 (18 октября 2026)

Сцена подключена к обычному экрану: **Кампании → Письмо у старого фонаря · воин**.
Выпускаемый ZIP явно использует mock AI и отдельный профиль. Механика — настоящий
Nat20. Выбран существующий воин со стандартным массивом, а не усиленный билд.
Разговор и осмотр домика читают только открытый авторский текст. Проверка
Внимательности разрешает вход во двор; сам вход — явная команда начала боя.
При подтверждённой победе письмо передаётся в той же транзакции, что награда Nat20.
Дальнейшие действия при 0 HP заблокированы; полная процедура смерти не заявлена.

Приёмка, результаты нового процесса и состав сборки: `reports/WINDOWS_PREVIEW_ACCEPTANCE.md`.
Описание ниже сохраняет прежний Python-only стенд и не является инструкцией запуска EXE.

Минимальный авторский модуль для проверки памяти на **настоящем Nat20 0.7.0**.
Использует существующие SQLite events/checkpoints, `Memory`, `ScenarioPackage`,
`Item` и `InventoryEngine.transfer`. Новых правил, мирового движка, импорта книги,
общих маршрутов и изменений UI нет. Все вызовы выполняются локально без моделей.

Данные:

- `examples/lantern-post/scene.json` — прежний `solo.world.ScenarioPackage`,
  как в `examples/world-scenario.json`: две локации, одна смотрительница,
  её открытые/личные сведения, скрытый след, узлы и короткая дорога.
- `examples/lantern-post/reward.json` — прежний `solo.inventory.Item`:
  одно благодарственное письмо. Это сюжетная вещь без боевых бонусов и цены.
- `tests/playable_scene_run.py` — фиксированный доверенный порядок прохождения
  для acceptance-проверки памяти; не новый игровой диспетчер или API.
- `tests/test_playable_scene_memory.py` — проверки сохранности и разграничения знаний.

## Запуск

Из корня SoloRealmsAI, в уже подготовленной среде с optional Nat20:

```powershell
.venv/Scripts/python.exe -X utf8 -B tests/playable_scene_run.py
.venv/Scripts/python.exe -X utf8 -B -m pytest tests/test_playable_scene_memory.py -q
```

Первый запуск создаёт временную SQLite, останавливается внутри активного боя,
запускает **новый процесс Python**, восстанавливает Nat20, доигрывает бой,
передаёт письмо и выполняет отдых. Печатает JSON с реальным результатом проверки,
победой, состоянием боя, HP, наградой и числом записей памяти. Временная база
удаляется по завершении; пользовательские кампании не используются.

Зависимости и локальный импортированный SRD уже закреплены в
`requirements-nat20.txt`, `vendor/nat20/UPSTREAM.json` и
`integration/nat20/imported/manifest.json`. `solo.nat20_content.release()` проверяет
версии, контрольные суммы кода/контента и профиль. При отсутствии пакетов подготовить
существующее optional-окружение по `integration/nat20/README.md`; тест не подменяет
отсутствующий Nat20 заглушкой и не скачивает данные сам.

## Порядок прохождения

1. Новая явно выбранная кампания Nat20, seed **5**. Герой — поддержанный
   human fighter 1 с longsword/chain-mail/shield из существующего native build.
   Его характеристики, производные значения и HP определяет Nat20.
2. `scene-install`: через `world.import_package` внутри `Store.record_scenario`
   добавляются домик и двор, герой оказывается у Лады. Письмо пока принадлежит
   NPC в существующем inventory. `import_package` назначает Ладе устойчивый ID.
3. `scene-check`: настоящий `GameCommand(check, check_id=perception)`.
   Навык, Сл и владение берутся из закреплённого `solo.nat20_content.CHECKS`,
   результат — из `resolve_check` Nat20. Данные модуля не назначают бросок/бонус.
4. `scene-enter`: доверенная сценарная транзакция проверяет **активное событие**
   Nat20 проверки. При успехе герой узнаёт про треугольную набойку, с отсылкой
   к `scene.json` и исходному `native_result`; при неуспехе этот факт не выдаётся.
   Открытая калитка позволяет войти во двор при обоих исходах. Лада остаётся
   в домике, поэтому не узнаёт ни результат осмотра, ни события боя.
5. `scene-start`: настоящий `start_combat(encounter_id=basic)`.
   Противник — **goblin-warrior**, профиль
   `integration/nat20/imported/encounter-profile.json`, ограниченный поддержанной
   обычной атакой Scimitar. Новые характеристики/действия в модуле не задаются.
6. `scene-move`: Nat20 проверяет перемещение героя в `(3,1,0)`.
   `scene-attack`: Nat20 разрешает атаку longsword по `goblin`.
   В этот момент сохраняется активный бой: инициатива, HP, экономика действий,
   родные события, replay recipe и память. Это **не** memory-v1 боевая фикстура.
7. Новый процесс вызывает `Nat20GameEngine.restore`: replay проходит через
   настоящий `start_combat/submit_player_intent/advance_monster_turn`, а контрольные
   суммы полного read-model сверяются с сохранёнными. Тест сравнивает весь
   восстановленный runtime и контекст памяти с состоянием перед перезапуском.
8. По очереди, возвращённой Nat20, выполняются реальные `attack`/`end_turn`.
   Ограничение в 20 команд — защита walkthrough от зависания, не расчёт боя.
   `end_combat` разрешается только после устранения противника.
9. `scene-reward`: сценарная транзакция проверяет принадлежность и активность
   исходного Nat20 события, `CombatOutcome.ended_reason == victory`, закрытый
   encounter этой сцены и отсутствие активного боя. Герой возвращается в домик;
   `InventoryEngine.transfer` передаёт существующее письмо от Лады герою.
   Награда не создаётся из текста Narrator или из придуманного loot Nat20.
10. `scene-rest`: настоящий `long_rest(food_water=False)` через Nat20.
    Время, HP, Hit Dice и ресурсы восстанавливает существующий native backend;
    письмо сохраняется в inventory Solo и не теряется при обновлении листа героя.

Seed и фиксированные request_id делают механический путь повторяемым.
UUID кампании/журнала/переданного Item меняются; они не являются механическим
результатом. Проверки сравнивают структуру и содержимое, сохраняя реальные ссылки
на события внутри каждой базы.

В проверенном проходе Nat20 вернул для Внимательности `natural_roll=5`,
`modifier=3`, `roll_total=8`, `dc=12`, `success=false`: скрытый след не раскрыт,
путь через открытую калитку остаётся доступным. Итог: **15 событий, 35 фактов**,
`ended_reason=victory`, активного боя нет, HP героя — **12**, письмо — **1**.
Это наблюдённые результаты Nat20, а не заданная модулем арифметика.

Проверки: 6 acceptance tests этой сцены прошли. После уточнения ID закрытого боя
повторный набор сцена + `tests/test_engine_memory.py` дал **37 passed**;
отдельный набор `test_engine_memory`, `test_pass17`, `test_world`, `test_inventory`,
`test_command_cycle` дал **104 passed**. Есть только предупреждения зависимостей
Lark/Starlette об устаревших интерфейсах. Общие тесты уже включают проверки адаптера,
поэтому числа наборов не следует складывать как независимые тесты.

## Что именно проверяет память

Типизированные effects настоящего `nat20_command` проецируются существующим
`EngineMemoryAdapter.project`: `truth=fact`, `provenance=confirmed_event`,
внешний `source_event`, внутренний `event_id`, ветка/as-of, subjects и
`source_ref` с версией Nat20, SRD/release digest и индексом effect.
Тест сверяет число записей с числом реальных effects **каждой** native команды,
проверяет родные `attack_rolled/damage_applied`, а не только готовый JSON снимка.
`outcome` команды и литературные описания фактами не становятся.

При закрытии native боя конечный GameSnapshot уже имеет `combat.id=none`.
Проекция памяти сохраняет ID **закрытого** боя и его участников из проверенного
`native_result.closed_combat`/предыдущего снимка, а не записывает «завершён бой none».
Тип результата проверяется существующим Nat20 `CombatOutcome`, согласованность ID —
по двум снимкам журнала; `source_ref` явно указывает дополнительный источник.

Для авторских фактов повторно используется `memory_evidence`, уже принимавшийся
`Memory.ingest`. Его явный `source_ref` теперь сохраняется вместо общей заглушки:
путь/поле данных сцены, а для следа и награды — также ссылка на Nat20 событие.
Это доверенный Python hook, не произвольный ввод AI.

Лада не добавляется фиктивным боевым актором. `EngineMemoryAdapter.context`
умеет выбрать канонический NPC из сохранённых `locations[].npc`, даже если его
нет среди акторов Nat20. Его механический пакет пуст, знания выбираются прежним
ACL. Снимок и знания читаются в одной SQLite read-транзакции и с одним as-of.

- Герой и Лада знают, что она видела следы.
- Только Лада знает о запасном ключе у сестры (`private`); герой этого не получает.
- Только герой может узнать про треугольную набойку из успешной проверки.
- Все родные броски/HP/личные ресурсы боя доступны по native ACL; Лада их не видела.
- О фактической передаче письма знают герой и Лада. Это не делает её свидетелем боя.
- Прежние `secret/gm` по-прежнему не сериализуются в контекст даже владельца.

Повтор исходной `GameCommand` возвращает прежний журнал, без worker и новых записей.
Повтор `scene-reward` возвращает прежнюю передачу. Попытка выдать письмо другим
request_id не создаёт вторую вещь. Сбой памяти в транзакции передачи откатывает
inventory, положение героя, журнал и ACL; повтор после исправления выдаёт ровно
одну награду. Победа и передача — две явные транзакции: после прерывания между ними
доверенный интегратор может безопасно повторить передачу по исходному victory event.

Undo восстанавливает native runtime и владение письмом; checkpoint хранит активный
путь истории. После undo атаки новая команда создаёт новую native ветку, использует
реальный replay и не получает будущую награду/знания заброшенного пути. Проверяется
также возврат между checkpoint завершённой сцены и checkpoint альтернативного боя.
Редактирование/повторное описание мастера не меняет ни Item, ни факты, ни знания NPC.

## Точный стык для интегратора

Этот модуль воспроизводимо проходится **доверенным Python walkthrough**. Он не
подключён к общему игровому экрану автоматически. Ограничение форматов и backend
не скрывается и не обходится временным удалением guard:

1. `ScenarioPackage.WorldEvent(kind=encounter)` принимает старый `MapDescription`,
   а не зарегистрированный Nat20 `encounter_id`. `AdventureDefinition.Effect.kind`
   тоже не содержит исполнения зарегистрированного Nat20 столкновения.
2. `Nat20GameEngine._preflight` сейчас отклоняет любой активный `state.adventure`
   и отложенные `world.events`. Поэтому `scene.json` содержит **пустой events**,
   не создаёт `state.adventure` и использует прежний допустимый импорт географии.
3. Нужна явная связь проверенного модуля/локации с **allowlisted `basic`** и
   native `check_id=perception`. Данные должны ссылаться на ID, не передавать
   характеристики, Сл, противников или произвольный код. Пока связь зафиксирована
   в walkthrough и этом документе; нового параллельного формата событий нет.
4. Для исполнения активного AdventureDefinition нужен доверенный обработчик
   сценарных последствий **в существующей транзакции Store.engine_event**:
   после получения native result/state, до окончательного `GameSnapshot` и
   проекции памяти. Он проверяет активный source event/command, применяет только
   разрешённые сценарные последствия, передаёт награду и выпускает evidence с ACL.
   Нельзя просто снять `_preflight` guard: существующий `adventure.after_transition`
   вызывается после создания engine snapshot, а сценарные изменения могут сделать
   снимок устаревшим или запустить прежнюю арифметику `Effect(kind=check)`.
5. До включения такого стыка общий маршрут должен сохранять текущий явный отказ.
   В этой работе `nat20_api`, `nat20_worker`, общий диспетчер, API и UI не меняются.

Покрытие ограничено этим поддержанным native профилем. Shortbow, Nimble Escape,
неподключённый advantage rider, произвольные заклинания и весь PHB не заявляются.
