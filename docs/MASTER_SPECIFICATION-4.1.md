# 1. ЦЕЛЬ ПРОЕКТА

Создай Solo Realms AI — полноценное игровое приложение, в котором один человек управляет одним главным героем, а локальная нейросеть выступает в роли Мастера подземелий.

Игрок должен иметь возможность:

- Загрузить готовое приключение PDF/TXT либо создать собственный мир.
- Загрузить лист персонажа, предысторию и книги правил.
- Настроить своего ИИ-Мастера.
- Общаться с NPC естественным русским языком.
- Диктовать действия голосом.
- Совершать сложные, нестандартные и условные действия.
- Участвовать в тактических боях.
- Использовать инвентарь, способности и заклинания.
- Исследовать живой мир.
- Влиять на NPC, фракции и сюжетные события.
- Обучать Мастера через вопросы и исправления.
- Сохранять и продолжать длительные кампании.

Приложение должно ощущаться как полноценная RPG с живым Мастером, а не как техническая панель работы с языковой моделью.

Главное качество системы — убедительный художественный отыгрыш, подкреплённый правильной игровой механикой и надёжной памятью.

# 5. ОСНОВНАЯ АРХИТЕКТУРА

Создай следующие логические подсистемы внутри одного приложения:

**Game Orchestrator**

Центральный координатор. Управляет игровым циклом, вызовами движков, подтверждениями действий и состоянием игры.

**Smart Action Router**

Преобразует ввод игрока в структурированное намерение.

**Rules Engine**

Проверяет игровые правила, действия, ресурсы и рассчитывает результаты.

**Scenario Engine**

Работает с готовыми приключениями, сюжетными узлами и их каноном.

**World Engine**

Поддерживает состояние мира, время, фракции, путешествия и последствия.

**Memory Engine**

Хранит и извлекает факты, воспоминания, историю, секреты и состояние NPC.

**Knowledge Engine**

Индексирует правила, книги и документы, возвращает проверяемые источники.

**Scene Compiler**

Готовит компактный пакет сцены для художественной модели.

**LLMAdapter**

Подключает одну локальную LLM с двумя режимами работы.

**Battle Engine**

Управляет тактическим боем, картой, позициями и инициативой.

**Inventory Engine**

Управляет предметами, снаряжением, деньгами и ресурсами.

**Voice Input Engine**

Распознаёт русскую речь в текст.

**Learning Studio**

Сохраняет подтверждённые исправления и решения пользователя.

**Master Configuration Studio**

Предоставляет графическую настройку художественной модели.

**Presentation Engine**

Объединяет игровые панели, графику и интерфейс.

**Save Engine**

Сохраняет события, снимки состояния, историю и резервные копии.

Это логические роли. Не превращай каждую из них в самостоятельный сервис или нейросетевой процесс.

# 6. ОДНА LLM — ДВА НЕЗАВИСИМЫХ РЕЖИМА

Это обязательное архитектурное решение.

Физически используется одна локальная GGUF-модель, загруженная в KoboldCpp.

Программно существуют два изолированных режима.

## 6.1. Interpreter Mode

Назначение: кратко и точно разбирать сложные действия игрока.

На вход поступают:

- Реплика игрока.
- Минимально необходимое игровое состояние.
- Доступные действия.
- Актуальные цели и объекты.
- Ограничения текущей ситуации.

На выходе — строго структурированный объект, проверяемый через Pydantic.

Он содержит:

- Тип намерения.
- Список предполагаемых действий.
- Порядок выполнения.
- Цели.
- Условия.
- Отрицания.
- Используемые предметы.
- Отложенные действия.
- Возможные развилки.
- Неясные детали.
- Необходимость подтверждения.

Режим не создаёт художественных описаний, не бросает кубики, не рассчитывает урон и не изменяет игровое состояние.

Используй ограниченный объём вывода, устойчивые параметры генерации и проверяемый JSON-контракт.

Если структурированный результат невалиден, допускается ограниченная корректировка или уточнение у игрока. Не запускать бесконечные повторные генерации.

## 6.2. Narrator Mode

Назначение: художественный отыгрыш Dungeon Master.

На вход поступает подтверждённый Scene Packet.

Модель отвечает за:

- Литературный русский текст.
- Диалоги NPC.
- Атмосферу.
- Эмоции.
- Мотивированное поведение персонажей.
- Описание окружающего мира.
- Драматургию.
- Художественное представление последствий игровых событий.

Модель не должна считать игровые характеристики, читать весь архив или менять механику.

Narrator Mode не имеет права напрямую выполнять SQL, Python, команды ОС или модификации состояния кампании.

## 6.3. Изоляция режимов

Interpreter и Narrator используют разные шаблоны промптов, схемы данных и параметры генерации.

Они не должны смешивать структурированный анализ с художественным ответом.

При переключении режимов не перезагружай веса модели.

Не рассчитывай на автоматическое сохранение KV-кеша между различными шаблонами: проверь фактическое поведение runtime и измерь выгоду.

# 7. SMART ACTION ROUTER

Разбор действия должен происходить по трём уровням.

**A. Прямое структурированное действие**

Клик по предмету, перемещение токена, выбор цели, использование игровой кнопки.

Обрабатывать программно без LLM.

**B. Быстрое известное текстовое действие**

Однозначные команды с понятной целью: простая атака, запрос характеристик, использование известного предмета.

Обрабатывать программно, если нет значимой неоднозначности.

**C. Сложная свободная реплика**

Несколько действий, отрицания, условные конструкции, косвенная речь, многоступенчатые планы, сложные социальные ситуации.

Использовать Interpreter Mode.

Не полагаться только на регулярные выражения при анализе сложных русских конструкций.

Обязательно различать:

- «Я атакую».
- «Я собираюсь атаковать».
- «Я не атакую».
- «Я атакую, только если противник нападёт первым».

Нельзя превращать намерение или условие в уже совершённое действие.

# 8. ПОДТВЕРЖДЕНИЕ И ИСПРАВЛЕНИЕ ДЕЙСТВИЙ

Это обязательное улучшение версии 4.1.

Для сложных, рискованных или неоднозначных действий перед применением механики показывай игроку краткий план:

**«Мастер понял твоё действие следующим образом…»**

В плане должны отображаться:

- Действия по порядку.
- Условия.
- Цели.
- Предполагаемые проверки.
- Возможные затраты ресурсов.
- Точки, где требуется дополнительный выбор.

Предоставь действия интерфейса:

- Подтвердить.
- Исправить.
- Отменить.

Игрок может редактировать первоначальную формулировку или отдельные пункты плана.

До подтверждения не выполняй необратимые изменения состояния.

Для простых однозначных действий допускается мгновенное исполнение без подтверждения.

Частота запросов подтверждения должна настраиваться.

Не заставляй игрока подтверждать каждую обычную реплику NPC.

После подтверждения игровая механика выполняется только один раз.

# 9. БЮДЖЕТ ВЫЗОВОВ LLM

Это обязательное требование производительности.

Установи целевые ограничения:

| Игровая операция | Целевой бюджет |
|---|---|
| Открытие инвентаря или журнала | 0 |
| Перемещение токена | 0 |
| Стандартный бросок через интерфейс | 0 |
| Обычный разговор с NPC | 1 |
| Простое текстовое действие | 1 |
| Сложное действие с условиями | 2 |
| Перегенерация только описания | 1 |
| Индексирование книг | Вне игрового цикла |
| Подготовка мира | В подготовительном режиме |

Для сложного действия два вызова означают:

1. Короткая интерпретация.
2. Художественный ответ после программного расчёта.

Дополнительные запросы допускаются при восстановлении после ошибок, но должны регистрироваться.

Не запускай скрытые многочисленные генерации для оценки одного игрового сообщения.

Показывай фактическое количество вызовов и их продолжительность в Performance Monitor.

Не конкурируй с активным отыгрышем за GPU.

Используй кеширование с версиями данных и точечной инвалидизацией.

Предзагрузка должна учитывать секретность: не передавай будущие сюжетные открытия в художественный контекст раньше времени.

# 13. ДВА РЕЖИМА КАМПАНИИ

## Campaign Mode

Пользователь загружает сценарий PDF/TXT.

Система определяет:

- Главы.
- Сюжетные узлы.
- Взаимоисключающие ветви.
- NPC.
- Локации.
- Противников.
- Секреты.
- Ловушки.
- Сокровища.
- Условия переходов.
- Условия повышения уровня.

Сохраняй исходный документ, страницы и происхождение информации.

Не выдавай предположения за извлечённые факты.

Игрок свободен отходить от сценария. Мастер учитывает последствия, не нарушая установленные факты.
