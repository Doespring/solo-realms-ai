# PDF → подтверждённый мир → Nat20: UI

18 октября 2026. Владение production-изменениями: **только `web/creation.js` и `web/prototype.js`**. Backend/API wiring, правила и DTO реализованы соответствующими владельцами; см. `PDF_NAT20_START.md`, `PDF_NAT20_RULES.md` и `PROTOTYPE_INTEGRATION.md`. Общий integration-документ здесь не редактировался. Full/EXE/build/live/paid не запускались; пользовательские профили и project DB/WAL не открывались.

Статус: **UI READY / source freeze**. Четыре целевых pytest-проверки прошли; реальный браузерный путь и завершение обоих процессов подтверждены.

## Пользовательский путь

1. «Новая игра» → существующая кнопка материалов приключения → загрузка файлов и описание. Дождаться извлечения. Старый прогресс 31/37 остаётся прогрессом обработки, а не готовым игровым миром.
2. **«Подготовить игровой мир»** → отдельное существующее тарифное согласие. В диалоге явно объясняется новый полный режим и возможность новых платных запросов. Выбирается редакция **источника**. Автоматической отправки книги, очистки блоков или переключения редакции нет.
3. **Локальная проверка мира выполняется автоматически** после подготовки, после восстановления и перед созданием кампании — отдельной кнопки нет. Частичная, names-only, изменившаяся или неподдержанная обязательная структура не открывает следующий шаг. Конкретные причины и ограничения отдельных операций видны на странице.
4. **«Подтвердить проверенный мир»** → отдельное локальное подтверждение выбранных run/revision. Перед отправкой UI повторно сравнивает текущую safe readiness с показанным выбором; устаревшее подтверждение отклоняется. Двойной клик не дублирует POST.
5. **«Выбрать героя Nat20»** → существующий конструктор, редактируемое имя, класс/вид/снаряжение и серверный Native preview. Игрок отдельно подтверждает героя, его предысторию и **D&D 2024 (Nat20)**. Изменение листа снимает подтверждение героя и требует новой проверки. Правила источника показаны отдельно и не переписываются.
6. **«Начать игру»** → существующий `/prototype/campaigns`, затем обычный игровой экран и command-turn. Для этого пути не вызываются legacy `/character/confirm` или `/play`. Подтверждённый мир без боёв передаёт пустой список встреч; UI не добавляет противника или сцену.
7. Сохранение остаётся служебной операцией. Перезапуск открывает сохранённое canonical state, продолжение идёт через тот же command-turn.

## Контракт UI

- `GET /creation/drafts/{id}/world-readiness`: только safe `scope`, `world_ready`, `ready`, `revision`, `run_id`, редакции, причины и `blocked_operations`. UI не читает приватные Draft.body, цитаты, секреты или внутренний формат Nat20.
- `POST /creation/drafts/{id}/confirm-world`: `{expected_revision,run_id,confirm:true}`. После безопасного ответа UI обновляет метаданные черновика и readiness. Не предполагает наличие private body.
- Полная подготовка: прежний `/prepare` с `world_structure:true`, редакцией источника, `consent_to_send:true` и новым `request_id`. UI запоминает идентификатор своего полного run и выбранную редакцию в локальном черновике, чтобы явное продолжение сохранило этот режим; хорошими блоками и кэшем управляет сервер.
- Старт: существующий CharacterBuildSpec без клиентских расчётов; `adventure:'prepared:<id>'`, `adventure_revision`, `mechanics_ruleset:'dnd2024'`, `rules_confirmed`, `hero_confirmed`, `background_confirmed`, `hero_background`. Флаги соответствуют отдельным действиям игрока. Локальные `world_run_id`/`source_ruleset` не отправляются как новые поля команды.
- Перед стартом повторно проверяются run/revision/world_ready/ready. Ошибка сохраняет ввод и управление, повтор использует тот же request_id. Конструктор также поддерживает выбор подтверждённого `scope:'world'` из существующего списка приключений.
- Hotfix.2 сохранён: прежняя локальная readiness и её ошибка дают 0 AI/prepare fallback, отдельный resume остаётся, история ошибок не перезаписывает актуальный результат. Mock блокирует подготовку через AI, но допускает локальную проверку/подтверждение и игру в уже подготовленном мире. Облачный путь не скрыт.

Это проверка UI-переходов, не доказательство извлечения пользовательского PDF.
- `tests/test_pdf_readiness_ui.py`: **1 passed**, 12.05 с, четыре регрессии hotfix.2.
- `tests/test_preview7_ui_followup.py`: **1 passed**, 10.94 с, шесть проверок, включая terminal/служебное восстановление/обычную Solo, consent и переключение cloud→mock.
- `tests/test_pdf_nat20_ui_real.py`: **1 passed**, 134.69 с, реальная приёмка нового API, Native builder, Nat20, памяти и отдельного процесса. Обе браузерные стадии и штатная остановка процессов прошли. Read-only native панели делают этот сценарий существенно дольше fixture-проверок.

Реальный сценарий использует общий backend test helper: настоящий короткий **синтетический** PDF импортируется и валидируется через offline MockTransport полного структурного ответа. Затем браузер работает с настоящими registered endpoints **без подмены игровых ответов**, AI — явно offline PreviewMock. Мир source-2014 подтверждён пользователем; human Rogue запускается с явно выбранными правилами 2024 и `encounters={}`. Осмотр → диалог с NPC с подтверждённым знанием о мосте → native dex check → служебное сохранение. Новый Python-процесс сравнивает хэш всего сохранённого Nat20 состояния; браузер сравнивает весь canonical snapshot и исполняет wis check с увеличением версии ровно на один. Итог: JavaScript ошибок **0**, legacy-вызовов **0**, скрытых prepare-вызовов **0**, memory.audit без замечаний в обоих процессах. Ранняя версия тестового стенда выявила незавершённые фоновые read-only запросы при остановке, поэтому финальный прогон дожидается network idle. Интерфейс ради теста не менялся. Первоначальное ожидание приватного `current.state.nat20` заменено правильной серверной проверкой: браузер получает только публичные данные; исправлена также опечатка отступа тестового helper.

## Точные ограничения

- Это source/browser проверка, не Windows EXE-приёмка и не доказательство качества подготовки пользовательской книги или живого ответа модели. Облачная подготовка проверена только явными fixtures/MockTransport, реальных вызовов провайдера — **0**.
- Обязательная неподтверждённая механика блокирует старт по серверной причине; необязательные таблицы/statblocks/эффекты не становятся исполнимыми автоматически. UI не рассчитывает лист, бой или законность действия.
- В public run пока нет обязательного признака режима подготовки. Свой full run UI помнит по ID локально. Для полного run, созданного вне этого UI или после очистки browser storage, следует явно выбрать «Подготовить игровой мир» и подтвердить этот режим; сервер решает переиспользование кэша. UI не угадывает режим по счётчикам 31/37.
- Источник и механика разделены; новый путь не мигрирует старые кампании и не меняет legacy-сохранения. Старый расширенный мастер сохранён отдельно.
- Native capability-панели выполняют фоновые read-only запросы, поэтому конец приёмки должен дождаться их завершения перед остановкой стенда. Это не платные вызовы и не игровые команды.

Очистка: собственные браузеры, Uvicorn и отдельный Python-процесс остановлены; проверка процессов с путём собственного стенда вернула **0**. Итоговые исходники, тесты, trace и снимки сохраняются. Проверка безопасности единственную попытку удалить проверенные неактивные временные профили отклонила: **blocked by policy**. Обход не выполнялся. Остались в `reports/pdf-nat20-ui/`: `tmp-fixtures-1`, `tmp-fixtures-final`, `tmp-hotfix`, `tmp-legacy`, `tmp-real-1`, `tmp-real-3`, `tmp-real-final` и устаревший `real-start-failure.png` (сбой раннего test helper, не актуальная ошибка UI). Ранее отклонённая очистка `reports/pdf-readiness-ui` не повторялась и не обходилась. Чужие стенды, рабочие профили, ZIP и материалы инцидента не затрагивались.
