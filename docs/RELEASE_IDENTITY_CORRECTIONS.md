# Корректировки к решению по идентичности релиза

Дата: 27 октября 2026. Второй независимый критик оспорил часть выводов; ниже — что подтвердилось,
что опровергнуто и что исправлено в `docs/RELEASE_IDENTITY_DECISION.md` и `docs/HANDOFF_BLESS_PARENT_PIN.md`.

## Подтвердилось (мои выводы были неверны — исправлено)

| Утверждение | Доказательство |
|---|---|
| Механика корпуса не менялась | strip-дифф всех 1663 файлов: 0 механических различий |
| Изменённых листьев | `name` и `description_localized`; файлов 690, а не 689 |
| Перевод имён виден игроку | `build_party.py:39`, имя в инициативе — это изменение контента, не только описаний |
| В корпус добавлен файл | `canonical/spells/ice-knife.json` (untracked, но учтён в пине и манифесте: 1664) |
| Документы Bless **пересекаются** с корпусом | 5 из 7 по `category`+`slug`: `spells/bless`, `classes/cleric`,
  `features/divine-order`, `items/mace`, `items/amulet`; расходятся байты |

Вывод «0 пересечений» в `docs/HANDOFF_BLESS_PARENT_PIN.md` был **ошибочным**: я проверял `list_slugs()`,
а расширение приносит собственные байты тех же документов. Значит `parent_release_digest` отвечает
на вопрос «какие байты родителя», и молчаливая замена его — тоже подделка. Документ поправлен.

## Опровергнуто (утверждение критика не воспроизвелось)

Критик предложил считать `runtime_hashes` по `reviewed` вместо `pinned` и получить `374afd1a…`.
Проверено:

```
по пину     : 33359fe3538b96bdb1bbde77
по reviewed : 8b8d6af9cfe5849c229f1d6b
HEAD-пин + HEAD-патчи        + текущий манифест: e837db2831b636fae6725a3d
HEAD-пин + HEAD-манифест                          : b682d5198fc9f185a5a4fa27
HEAD reviewed + HEAD-манифест                     : 19c90a34ec9c643800b11d43
цель                                              : 374afd1a3898e089e023130c
```

Ни одна комбинация не даёт `374afd1a…`. Дополнительно выяснено, что в `HEAD` манифест `prototype-srd-2024-v1`
содержал **0 документов**, а сейчас 12 — то есть состав манифеста тоже менялся. Простая замена источника
хешей на `reviewed` не возвращает старый отпечаток.

## Что остаётся верным в решении

- `374afd1a…` не восстанавливается ни одним из проверенных способов; отказ остаётся единственным
  проверяемым поведением.
- Подстановка нового дайджеста в фикстуру — подделка, это подтвердил и критик.
- Решение не менять `parent_release_digest` Bless без согласования — тем более верно после того,
  как выяснилось про пересечение документов.

## Что исправлено в моих тестах по замечанию критика

Оба переписанных теста прошли мутантов («воркер принимает любой дайджест», «`release()` всегда текущий»),
то есть ловили только текст ошибки, а не источник. Добавлено:

- `tests/test_nat20_dash.py` проверяет, что ограничение «`dc` только с `source='master'`» держится на модели,
  а не только на тексте ошибки.
- Тавтологичные сравнения фикстуры с самой собой убраны там, где они не несут смысла.

## Остаётся открытым

- Путь «initialize → end_turn → version+1» для старого сохранения не восстановлен: он требует либо
  реестра исторических релизов (второй корень данных, ~12,4 МБ на релиз), либо явной миграции состояния
  из `hero`/`sheet`/`definition` вместо replay боя. Ни то, ни другое не делалось.
- `initial_digest` в фикстуре `12cb4446…` не воспроизводится (`start_combat` даёт `95843be6…`), то есть
  снимок снят после двух команд. Фикстура как эталон воспроизведения несостоятельна независимо от моих правок.
