Разрешены владельцем 23 октября 2026. Это два checkout одного Git-репозитория, не два движка и не две конкурирующие версии продукта.

Каждый чат и его субагенты должны работать в назначенной папке. Разные вкладки, открытые в одной папке, НЕ обеспечивают независимости. Не требуется менять глобальные настройки Harness или отключать защиту.

Общий поток продолжает текущие исправления приложения. Поток движка отдельно реализует и проверяет изменения Nat20. Оба могут читать соседнюю копию, но не писать в неё. Git metadata общие, рабочие деревья и index отдельные. Никто не переключает ветку другого чата.

## Передача движка

1. Поток движка фиксирует свою исходную контрольную точку; её commit записан в собственном `runtime/engine-workspace-baseline.json`. Это setup/baseline, не набор новых механик для переноса.
2. После неё делает небольшие тематические коммиты. Для поставки выбирает изменения ядра и тестов, а не весь diff ветки с её AGENTS и настройками окружения.
3. Создаёт `integration/engine-handoff/DELIVERY.md`: base/head commits, список файлов/функций, версия ядра и корпуса, schema/digest, новые публичные API и примеры, совместимость/миграции, результаты обоих критиков и тестов. Приложить узкий patch или список коммитов.
4. Если нужен host-адаптер, движок описывает контракт и ожидаемый результат. Общий чат сопоставляет это со своим текущим кодом и сам меняет `solo/nat20_worker.py`, `nat20_api.py` и другие адаптеры. Двигать правила в host ради удобства нельзя.
5. Общий чат сохраняет checkpoint, проверяет соответствие старых байтов и применимость patch, затем принимает выбранные изменения и прогоняет интеграционную сессию. При несовпадении исходной версии — согласует изменения, а не выполняет принудительный merge/overwrite.
6. На исходном коммите b4ddf408 Nat20 уже отслеживается Git (1764 файла); раннее замечание аудита о неотслеживаемом vendor относится к прежнему состоянию. При принятии снова проверить текущую отслеживаемость, байты и зависимости. Не переносить setup-коммит целиком и не перезаписывать локальные изменения автоматически. Никакого `git add .`.
7. Обновлённый движок становится используемым в приложении только после явного переключения manifest/binding и проверки старых сохранений. Новые байты получают новый digest.

Независимость разработки не означает независимость контрактов: изменение API/формата состояния оформляется предложением в DELIVERY до массового переписывания. Не требуется останавливать общий чат на весь период разработки движка; короткое окно принятия изменений согласуется при готовности поставки.

Никакого автоматического обмена сообщениями между чатами: передаваемые документы/патчи доступны владельцу. Денежный бюджет один, живые профили не используются для параллельных тестов. По умолчанию оба потока проверяются локально.
