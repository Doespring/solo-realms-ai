# Задача изолированного чата Nat20

Владелец разрешил реализацию, а не только аудит. Рабочая папка — этот checkout `SoloRealmsAI-Nat20`, ветка `work/nat20-engine`. Не меняй соседнее приложение. Следуй местному AGENTS.md.

## Цель

Расширять и адаптировать один Nat20 под D&D 2024, с русскими именами/терминами, проверяемыми расчётами и версионированной поставкой для Solo. Основной чат параллельно исправляет приложение и затем принимает твою поставку. Тебе не требуется ждать завершения общего редизайна/аудита, а общему чату — твоего полного покрытия всех книг.

## С чего начать

1. Прочитай актуальные `reports/NAT20_DND2024_AUDIT_STAGE_ABC.md`, `reports/NAT20_DND2024_COVERAGE.json` и блок A `docs/DEEPSEEK_DND2024_ENGINE_AND_CHAT_DESIGN_PROMPT.md`, если они присутствуют. Это материалы для проверки, не обязательство верить каждому выводу. Исторический путь основного проекта внутри них не меняет рабочую папку.
2. Обязательно используй разработчиков, независимого критика и критика критика той же модели DeepSeek. Раздели файлы и проверяй результат.
3. Проверь существующие механизмы перед добавлением новых. В частности, `use_item` может проходить через общий `native_action` → PlayerIntent; отсутствие отдельной строки вызова в Solo не доказывает мёртвый путь. Свежий процесс сам по себе не гарантирует идемпотентность host-транзакции.
4. Начни с исполняемого примера магического предмета: надевание/настройка → механический эффект → снятие/прекращение → сериализация → восстановление. Для Adamantine Armor докажи изменение обработки критического попадания согласно источнику, а не только наличие Foundry-флага.
5. Затем настройка/предпосылки, заряды и восстановление по триггеру, активации, варианты и таблицы. Сравни корпус Nat20 и 257 извлечённых записей по идентичности/вариантам/источнику; число 296 не доказывает более полную реализацию.
6. Закрывай следующие пробелы механики по проверяемой матрице доступного SRD/источников. Различай данные, исполнение, проверку и будущую интеграцию. Не делай новый большой этап каталогизации вместо кода.

Основной открытый источник — SRD 5.2.1, https://www.dndbeyond.com/srd . Версию, страницы и errata фиксируй. Частные книги не распространяй.

Это разные каталоги: сопоставь версию/хеш, а не считай их одной базой. Русский бестиарий проверяется на редакцию; перевод проекта не выдаётся за официальный.

## Окружение и проверки

Используй собственную `.venv` и `requirements-nat20.txt`. Из неё должны импортироваться dnd5e_engine и dnd5e_srd_data из локального vendor ЭТОГО checkout. Не переустанавливай editable-пакеты в .venv основного приложения.

Локальные проверки ядра не требуют облачного API. Сохраняй исходные bytes/manifest как baseline. Изменения расчётов должны иметь независимые ожидаемые результаты по источнику, отрицательные случаи и проверку round-trip состояния. Показывай честные ограничения, не ослабляй assert или guards ради PASS.

Тестовые файлы/базы только в собственном runtime. Если поднимаешь отдельный сервер, используй свой профиль и другой порт, например 19225; основной 19215 не останавливать. Ограничения sandbox не обходить.

## Поставка и продолжение

После каждого законченного механического участка подготовь `integration/engine-handoff/DELIVERY.md` по `docs/PARALLEL_WORK_PROTOCOL.md`. Отдельно укажи, какие адаптеры должен изменить интегратор. Можно готовить пример/patch для его рассмотрения в своей папке, но нельзя менять файлы основного приложения или обещать уже работающую интеграцию без её проверки.

Веди `reports/ENGINE_WORKSPACE_PROGRESS.md` и продолжай реализацию после промежуточных сводок. Не запрашивай новое разрешение на код из-за исторического AGENTS. Доступ к платному API и увеличение общего прежнего тестового бюджета при этом не выдаются заново.
