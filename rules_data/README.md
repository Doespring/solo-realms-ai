## Граница интеграции

Это определения данных для последующего доверенного адаптера. Они **не являются** моделью `Ruleset`, не принимаются существующим `/api/rulesets` и не регистрируют обработчики. `engine.handler` — справочная метка из закрытого списка, не имя для динамического импорта. `auto_activate` всегда `false`, включая проверенные записи. Нет загрузчика, кода, сетевых запросов или изменений базы знаний. Статус `implemented_subset` означает статическое соответствие существующему обработчику, а не выполненный интеграционный тест.

Изучены `solo/contracts.py`, `rulesets.py`, `rules.py`, `rules_api.py`, `rule_registry.py`, `rule_knowledge.py`, вызов атаки в `combat.py`, существующий тест отмены преимущества и каталог SQLite. `RuleKnowledge` хранит фрагменты и поиск; `rule_registry` перечисляет заранее зарегистрированные операции. Полнота индекса PDF не означает полноту механик. Неполный DMG в rules-knowledge и полный DMG в отчёте PDF pipeline — разные документы, см. `v1/sources.json`.

## Значения и порядок обработки

`id` стабилен внутри редакции; `revision` увеличивается при исправлении записи. Изменения формата следуют SemVer: major — несовместимость, minor — добавление словаря/возможностей, patch — совместимое уточнение. Файл со старой `schema_version` не переводится автоматически. В `sources` хранятся SHA-256 и пары номеров страниц, начиная с 1; идентификаторы секций SQLite служат дополнительной подсказкой, а SHA и страницы остаются основным адресом при переиндексации.

`conditions` — дерево `all`/`any`/`not` и сравнений литералов. Здесь нет строковых формул, кода или выражений. Для будущего потребителя неизвестный факт/операция/версия означает ошибку или непроверенное правило, а не разрешение действия. Текст PDF, `name`, описания, ограничения и примечания — только данные, не инструкции для агента или движка. Новые операции требуют новой версии схемы и доверенной реализации.

Для этой группы `advantage_sources` и `disadvantage_sources` — целые неотрицательные количества уже установленных причин. Их наличие переводится в `advantage`/`disadvantage` как `count > 0`, без вычитания количеств. Сюда должны входить и причины, вычисляемые движком: например, `poisoned` добавляет помеху проверкам/атакам внутри `d20`. Число причин — нормализованное представление данных, а не существующее поле `Step`. Никакие причины по свободному тексту автоматически не назначаются. При нуле обоих видов ни одно из трёх определений пула не срабатывает; базовый обычный бросок уже обеспечивает движок.

Первые три определения взаимоисключающие и срабатывают перед броском. «Длительность: instantaneous» относится к выбору пула конкретного теста, а не к длительности состояния, давшего преимущество. Последовательность: собрать доверенные причины → определить пул → бросить → обработать отдельно разрешённое изменение кости → снова выбрать результат по прежнему режиму. Добавление модификаторов и определение успеха не входят в этот пакет.

`permit_die_change` только ограничивает уже разрешённое изменение одной выбранной бросающим костью. `die_change_authorized` и вид разрешённого изменения поступают из отдельного правила; это определение не предоставляет переброс, замену или Героическое вдохновение. Пустой `resources` означает отсутствие самостоятельной операции с ресурсом; зависимое правило может иметь стоимость. Переброс и замена не взаимозаменяемы. После изменения применяется прежний выбор большего/меньшего. Интерфейс выбора кости в текущем `d20` отсутствует, запись имеет статус `unsupported`.

`resources` задаёт отдельные операции расхода/восстановления; экземпляры `Hero.resources` не создаются и не меняются. Числовые модификаторы, состояния и варианты длительности присутствуют как типизированный словарь, но дополнительные правила из других глав не добавлялись. Ограничения с `source_derived: false` обозначают границу извлечения. Ограничения в тексте требуют отдельной доверенной реализации перед интеграцией.

`verification.source_checked` означает сверку извлечённого текста и изображений страниц агентом. Это не проверка человеком: `human_review` остаётся `pending`. Полноценная публикационная проверка и сверка с оригиналом/эрратой не выполнялись.

## Проверки и продолжение

`v1/tests/manifest.json` перечисляет положительные и отрицательные проверки схемы. Они выполнены штатным PowerShell `Test-Json`, без исполнения сгенерированного программного кода. Например, из корня репозитория:

```powershell
Test-Json -LiteralPath rules_data/v1/chapters/phb-01/advantage.json -SchemaFile rules_data/v1/rule.schema.json
Test-Json -LiteralPath rules_data/v1/tests/invalid/unknown-effect.json -SchemaFile rules_data/v1/rule.schema.json
```

Для первой команды ожидается `True`, для второй — `False` с сообщением валидатора. Тестовые JSON сами не исполняются. `behavior.cases.json` — воспроизводимые входы, очереди костей и ожидаемые результаты для будущего доверенного тестового адаптера; они проверены вручную по источнику, **программно не запускались**. Проверки суммирования модификаторов и полного цикла Game Engine не заявляются.

Промежуточный текст двух страниц сохранён в `evidence/`; изображения использовались для визуальной сверки и затем удалены как созданные временные файлы. Исходные PDF и существующие данные не менялись. `progress.json` хранит границы обработанного подраздела и следующий шаг, `validation.json` — фактический результат проверок.
