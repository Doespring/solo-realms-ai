# n12 — «Тестовые данные · mock» не попадает в обычную сборку

Дата: 07.11.2026, стенд — HEAD `4e495724` (n11) + незакоммиченная правка `web/play.js`.
Задача: t_82cd8363.

## Что было

Метку ставил опрос `/api/health` в `web/play.js:217`:

```js
$('model-status').textContent = h.llm?.mock ? 'Тестовые данные · mock' : …
```

То есть **любой** запуск с тестовым адаптером (в том числе стенд аудита, с которого
критик №2 снимал кадры) писал в шапку «Тестовые данные · mock» на всех экранах.
Флаг в URL аудита (`?audit=game-1440`) ничего не решал: условие смотрело только на `/health`.

## Что сделано

`web/play.js:210-217` — метка теперь под явным флагом:

```js
function mockBadge(){ const q=new URLSearchParams(location.search);
  return q.get('audit')==='1'||q.get('mock-badge')==='1'; }
async function health(){ const h=…
  textContent = mock&&mockBadge() ? 'Тестовые данные · mock'
              : ready&&!mock ? 'Облачный Мастер доступен'
              : h.llm&&!mock ? 'Облачный профиль настроен'
              : 'Подключите облачного Мастера'; }
```

- По умолчанию (без `?audit=1` / `?mock-badge=1`) тестовый адаптер показывается
  как «Подключите облачного Мастера» — облачного Мастера в нём действительно нет.
- `?audit=game-1440` (URL, которым снимает кадры `tools/ui_audit.py`) флагом **не считается**:
  иначе критик снова увидел бы метку на замере.
- Логика подготовки и mock-режим подготовки книги (`web/creation.js`,
  `#creation-mock-notice`) не тронуты — он нужен n11.

## Проверка (не описание, а вывод)

Новая проба `tools/probe_mock_badge.py` поднимает **свой** стенд (порт свободный,
свой `--data-dir`; порт 19215 и профиль владельца не трогаются), снимает 1440×900
через CDP и читает DOM, а не картинку.

```

.venv/bin/python tools/probe_mock_badge.py --stand plain --out reports/n12/plain
```

Стенд `mock` (тестовый адаптер, `/api/health` → `{"result":"MockLLM (тест)","mock":true}`):

| кадр | URL | `#model-status` | «Тестовые данные» в DOM |
|---|---|---|---|
| главная | `/?theme=dark` | Подключите облачного Мастера | нет |
| создание книги | `/?theme=dark` | Подключите облачного Мастера | нет |
| кадр аудита | `/?theme=dark&audit=game-1440` | Подключите облачного Мастера | нет |

Стенд `plain` (обычная сборка `~/.hermes/scripts/serve_solo.py`, `/api/health` без `llm`):
во всех четырёх кадрах «Подключите облачного Мастера», `bodyHasMock=false`,
`bodyHasTestData=false`, `visibleMock=[]`. Флаг `?audit=1` в обычной сборке метку
не выдумывает.

Итог пробы: `checks.ok = true` на обоих стендах, замеры — `reports/n12/*/n12-measures.json`.

**Какой стенд что доказывает.** Дискриминирующий — `mock`: его `/api/health` отдаёт
`mock:true`, и старый код (`h.llm?.mock ? 'Тестовые данные · mock'`) ставил метку на каждом
кадре. Сейчас на нём же, без флага, метки нет — это и есть «было/стало». Стенд `plain`
отдаёт `/api/health` без `llm`, поэтому старый код там метку и не поставил бы: он
подтверждает только, что обычная сборка чиста и что флаг ничего не выдумывает.
Независимый критик (субагент) прогнал обе пробы на `ddf694af` сам: `ok: true` на обоих,
4/4 проверки, `2 passed`, кадры посмотрел глазами — вердикт PASS.

## Ограничения (честно)

1. На стенде с тестовым адаптером экран создания книги показывает плашку
   «В этой тестовой сборке работает mock-Мастер…» (`web/creation.js`,
   `#creation-mock-notice`). Это mock-режим подготовки книги — по заданию его не
   трогали (нужен n11). Владелец на своём стенде её **не увидит**: `/api/health`
   на `127.0.0.1:19215` отдаёт `llm.{"result":"RouterAI / deepseek…","cloud":true}`
   без признака `mock`, плашка показывается только при `llm.mock===true`.
2. Проба мерит шапку и видимый текст, а не пиксели: читает `#model-status`,
   `header.innerText` и листовые узлы с геометрией. Скриншоты приложены для глаза.
3. Перезапуск стенда не нужен: `web/` отдаётся с диска (`app.mount('/static', …)`),
   и `curl` уже видит новый `play.js`. Браузер владельца обновится по ETag.
