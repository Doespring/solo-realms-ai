# r239 — вход по главе 1 на книге 323 страницы: живая проверка

Проверка шла **руками через интерфейс** живого приложения `127.0.0.1:19215`
(сборка `commit=1d699c6e`, r237; профиль `runtime/web-local`), на телефоне 375×812,
DPR 2. Книга — «Icewind Dale — Rime of the Frostmaiden RUS.pdf», **323 страницы**
(ровно та книга, что в карточке; физически 137 МиБ).

## Плохое первым

1. **Число r237 «вход за 8 с» на книге 323 страницы не подтвердилось: вход открылся
   за 3 мин 56 с.** Причина не в старте, а в нарезке: на этом объёме (1 277 375 знаков)
   секция в 40 тыс. знаков не влезает в потолок ответа роли (2048 токенов), ответ
   обрывается по `finish_reason=length`, секция делится пополам, а деление добавляет
   блоки и ставит половины в очередь за слотами (4 одновременно). r237 мерил на срезе
   428 404 знака (109 страниц) — там секции были 20–33 тыс. и влезали.
2. **Полный разбор идёт не «минуты»:** на 14-й минуте было 24 блока из **64**, оценка
   остатка по `progress.eta_s` — **23:42**, то есть около **38 минут** на книгу
   (у r237 — 2:47). Блоков стало больше исходных 52 (52 → 54 → 56 → 57 → 60 → 61 → 64)
   именно из-за делений: `structure.limit_hits` растёт вместе с `split_sections`.
3. **Кнопки на экране не появлялись после перезагрузки, хотя глава была готова** — это
   дефект из пункта 4 карточки, и он найден и починен (ниже). До правки: полоса висела
   на «Подготовка · 0:00» без чисел, панель мира не рисовалась вовсе, кнопки
   «Подтвердить проверенный мир» и «Выбрать героя Nat20» не появлялись никогда.
4. **Первое нажатие «Подтвердить героя» после ввода имени не делает ничего** — нужен
   второй тап. Гонка: тап снимает фокус с поля имени → `change` запускает
   `syncContract()` (сеть) → обработчик нажатия успевает проверить `confirmReady()`
   до её ответа. Не чинилось: вне карточки, записано в «кандидаты».
5. **Вход пустой по содержанию:** стартовая сцена «Десять Городов», мест 7, **NPC 0**.
   Ходы «иду к дому и стучу», «спрашиваю хозяина» получают штатный отказ движка
   «Здесь нет доступного собеседника. Выберите другое действие.» Игра при этом не
   рвётся, но поиграть в главу 1 пока можно только осмотром.

## Дефект, который починен

`web/prepare-progress.js:140`:

```js
const state=panels.get(host);
if(!state){panels.set(host,build(host));startClock(state,run)}   // state ещё undefined
```

`build()` возвращает новое состояние полосы, но `startClock` получал старую переменную
(`undefined`) и падал на первом кадре. Исключение вылетало из `drawProgress` →
`drawPreparation` → `drawFiles` → `open()`, поэтому **не доходило** до `poll=setInterval(...)`:
страница, открытая посреди подготовки (владелец обновил вкладку, вернулся в приложение),
не обновлялась больше никогда. Видно ровно то, о чём пункт 4 карточки: глава разобрана,
а кнопки нет.

На скриншоте `01-progress-playable-375.png`, снятом **до** правки, этот отказ виден
буквально: всплывающее сообщение «Cannot read properties of undefined (reading 'timer')»,
полоса без чисел, панели мира нет.

Правка — две строки: `let state=...` и `state=build(host);panels.set(host,state);startClock(state,run)`.
Плюс `web/index.html`: `prepare-progress.js?v=sims-4 → sims-5`, иначе у владельца
остался бы кэш.

**Приёмка правки** (перезагрузка страницы посреди того же прогона, кэш отключён):

- полоса: «Можно играть», часы 8:32, тики 1…60, подпись «Выписываю имена тех, кто встретится…»;
- панель мира: «Структура мира проверена. Требуется ваше подтверждение.», кнопка
  «Подтвердить проверенный мир» активна, «Подготовить игровой мир» заперта;
- после подтверждения появляется «Выбрать героя Nat20» — то есть путь до игры проходит.

Скриншоты (все 375×812, DPR 2): `01-progress-playable-375.png` (до правки — полоса
без чисел и без панели мира), `02-progress-playable-375.png` (после правки — «Можно

## Дополнение: чем кончился прогон

Прогон `2e18c595…` закончился **`partial`**: 96 из 96 блоков, 0 упавших, но мир не
собран целиком (`ready=false`). Итог по часам и деньгам:

| что | число |
|---|---|
| полный разбор книги | **3275,5 с = 54 мин 36 с** (r237: 2:47) |
| блоков | план 52, к концу **96** (44 секции поделены) |
| `structure.limit_hits` / `split_sections` | **44 / 44** при `output_limit_tokens=2048` |
| минимальный запас до потолка | **16,9 %** (`min_headroom` 0,1686) |
| самый большой ответ | 115 642 Б |
| оплаченных вызовов / деньги | **141 / 22,84 ₽** (в r237 — 17 / 1,02 ₽) |
| мир | мест 7, NPC 0, **55 сущностей в карантине**, `ready=false` |

**Второй дефект (нашёлся после полного разбора, кандидат в карточку).** Как только
прогон перестаёт быть `running`, вход пропадает с экрана: `GET …/world-readiness`
отвечает `ready=false, world_ready=false` с причиной «Подготовка не завершена:
96 / 96. Продолжите сохранённые блоки.», кнопки «Подтвердить проверенный мир» и
«Выбрать героя Nat20» скрыты (скриншот `11-final-375.png`). Причина в коде:
`solo/preparation_pipeline.py:344` пропускает вход только при
`playable and started`, где `started` — это `queued`/`running`. То есть «Можно играть»
существует **ровно пока идёт чтение**; на книге, где полный мир заведомо не проходит
канон (а r237 сам это и описал), после дочитывания начать новую игру с этого экрана
нельзя. Текст причины при этом врёт: 96 из 96 разобраны, продолжать нечего
(`failed=0`, блоков для повтора нет). В этом прогоне владельца спасло только то, что
кампания была создана заранее, во время «Можно играть».

Правку этого гейта здесь не делал: это меняет контракт входа (вход живёт дольше
прогона), а не только вёрстку, и требует отдельного решения — карточка r239
разрешала чинить «кнопку нет», но не переписывать правила готовности мира.

## Два наблюдения про `health`, чтобы ими не обманулись

1. **`health.commit` — это HEAD сейчас, а не код запущенного процесса.** В
   `solo/build_identity.py:84` коммит берётся `git rev-parse --short HEAD` на каждый
   запрос. Пока шёл мой прогон там было `1d699c6e`, после моего коммита — `4e7df6d3`,
   хотя процесс не перезапускался. Код процесса показывает только `build`
   (`bed6d0493e1e`, хеш загруженных модулей) — он и оставался неизменным. Сверять
   «health.commit с HEAD» как признак свежести сборки бессмысленно: они совпадут всегда.
2. **`health.llm.connection_verified` стал `false`, хотя вызовы проходили минуту
   назад** (последний `preparation_world` — 05:43:39, ok). В `solo/cloud.py:162` это
   `bool(self.last_connection)`, то есть отметка последней проверки связи, а не
   доступность провайдера. Как индикатор «Мастер доступен» она даёт ложную тревогу.
