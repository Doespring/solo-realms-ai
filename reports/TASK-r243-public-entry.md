# r243 — публичный вход: туннель не должен умирать молча

Дата: 2026-11-06. Дерево: `/home/hermes/projects/SoloRealmsAI-Nat20` (код не менялся —
правка инфраструктурная, вне Git).

## Что было сломано (плохое первым)

1. **Юнит туннеля мог навсегда остаться в `failed`.** У `cloudflared-solo.service`
   стояло `Restart=always`, но с системным лимитом стартов по умолчанию
   (`StartLimitBurst=5`, `StartLimitIntervalSec=10s`): после пяти падений за десять
   секунд (обрыв сети, отказ DNS, 429 от trycloudflare) systemd переставал
   перезапускать юнит и **сам его уже не поднимал** — вход мёртв до человека.
2. **Рестарт меняет адрес, и об этом никто не узнавал.** `cloudflared tunnel --url` —
   это account-less quick tunnel: при каждом старте процесса он получает **новый**
   поддомен `*.trycloudflare.com`. Адрес нигде не сохранялся; в журнале он есть, но
   владелец его не читает. Итог: туннель «поднялся», а закладка в телефоне мертва.
3. **Не было проверки «а вход правда работает».** Процесс может быть жив, юнит
   `active`, а снаружи 530: журнал cloudflared за сутки показывает регулярные
   `no recent network activity` и перерегистрации на edge. Живучесть процесса
   ничего не говорит о доступности адреса.

## Что сделано

- Drop-in `~/.config/systemd/user/cloudflared-solo.service.d/r243-selfheal.conf`:
  `StartLimitIntervalSec=0` (лимит стартов снят — состояние `failed` для этого юнита
  недостижимо), `RestartSec=10` (было 5). `OOMPolicy` и `MemoryMax=256M` не тронуты.
- Сторож `~/.hermes/scripts/solo_entry_health.py` + user-таймер
  `solo-entry-health.timer` (`OnUnitInactiveSec=60`, oneshot; `OnUnitActiveSec` на
  oneshot даёт пустой NEXT — таймер не срабатывает вовсе). Проверяет три звена:
  мост `127.0.0.1:19999/__health` → `systemctl --user is-active cloudflared-solo` →
  снаружи `https://<адрес>/__health`.
- Сторож держит актуальный адрес в `~/.hermes/solo-entry-url` и пишет в топик
  проекта одну строку, когда адрес сменился или вход отвалился/вернулся.
  Доставка — прямым вызовом Telegram API из `.env`, не через гейтвей: сообщение
  уходит и тогда, когда гейтвей лежит. Токен и пароль не печатаются никуда.
- Устойчивость логики: одиночный сетевой блип не будит владельца (нужно
  подтверждение два прогона подряд), а перед собственным рестартом сторож ждёт
  окно `RestartSec` systemd (`activating`), чтобы не перезапустить туннель дважды —
  каждый лишний рестарт стоит нового адреса.
- Самопроверка вердиктов: `~/.hermes/scripts/solo_entry_health_selftest.py`
  (подменяет сеть, systemd и файлы состояния; реальный туннель не трогает).
  Четыре сценария: транзиентный сбой → молчание; подтверждённый отказ → одно
  сообщение; восстановление → одно сообщение; смена адреса → одно сообщение.
  Вывод: `ИТОГ: все проверки прошли`, exit 0.

## Ограничения и что осталось решением владельца

1. **Постоянной ссылки у бесплатного quick tunnel не бывает.** Адрес меняется при
   каждом старте процесса; сторож делает это безопасным (пишет новый адрес в топик
   и в `~/.hermes/solo-entry-url`), но закладку в браузере телефона придётся обновлять.
   Для постоянного адреса нужен **именованный туннель Cloudflare** — аккаунт,
   домен и токен. Это вопрос владельцу: без его аккаунта такое не настраивается.
2. **Второй, параллельный путь остался как есть.** `solo-public.service` держит тот
   же мост и по кругу поднимает сторонние туннели (pinggy / localhost.run / serveo),
   складывая адрес в `~/.hermes/solo-public-url`. По журналу эти адреса живут
   12–60 минут, то есть как закладка не годятся. Предложение: оставить как резерв,
   но канонический адрес брать из `~/.hermes/solo-entry-url`. Убирать юнит без слова
   владельца не стал.
3. **Ветка «юнит уже в `failed` → `reset-failed` + restart» живьём не проверена:**
   `systemctl --user stop cloudflared-solo` заблокирован политикой headless-режима
   («dangerous command without a user present»). Проверено косвенно и надёжно:
   с `StartLimitIntervalSec=0` при `Restart=always` юнит не может уйти в `failed`,
   поэтому ветка — страховка, а не рабочий путь. Живой путь падений (kill -9)
   проверен дважды.
4. `cloudflared` держит `MemoryMax=256M`; при его упоре в лимит туннель будет
   перезапускаться и менять адрес. Лимит по запрету задачи не трогал.

```bash
tail -20 ~/.hermes/logs/solo-entry-health.log
```
