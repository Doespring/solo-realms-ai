# Почему разработка не превращается в доступную игру

Дата: 22 октября 2026, Europe/Samara. Объект: Solo Realms AI.

Это диагностика текущих исходников, тестов, отчётов и работающего локального сервера. Исходники приложения, настройки, сохранения и процессы при аудите не менялись. Новые тесты и платные AI-вызовы не запускались. Старые числа PASS взяты из отчётов, а не получены повторным прогоном.

## Вывод

Работа не стоит на месте на уровне отдельных исправлений. Застопорилась **интеграция в один доступный игроку продукт**. Новые задания часто проверяются на другом входе, другом механическом пути, другом состоянии данных и новом тестовом сервере. В работающем приложении эти условия одновременно не выполняются.

Идея текстовой игры с материалами и Nat20 остаётся осмысленной. Ошибка порядка работ — одновременно расширять универсальность анализатора, полноту механики и сложность редактора, не закрепив один повторяемый игровой сеанс. Ни число изменённых строк, ни сумма локальных тестов не измеряют достижение этого результата.

## 1. Подтверждённый разрыв между файлами и работающим сервером

Слушающий порт 19215 процесс Python PID 22560 запущен 21 октября в 16:15:25. Файлы менялись позднее:

| Файл | Время изменения 21 октября |
|---|---|
| `solo/prototype_ui.py` | 22:49:12 |
| `solo/nat20_wizard.py` | 22:49:39 |
| `web/wizard.js` | 22:50:50 |
| `web/chronicles.js` | 23:05:24 |
| `web/character-creation.js` | 23:13:36 |

Время само по себе не доказывает несовместимость, поэтому проверено поведение:

- GET `/openapi.json` работающего сервера содержит `/api/prototype/wizard/contract`, но **не содержит `/api/prototype/wizard/recommend`**;
- этот маршрут есть в текущем `solo/prototype_ui.py`;
- GET `/static/wizard.js?v=wizard-7` уже отдаёт JS, который вызывает `/prototype/wizard/recommend` и использует новую схему черновиков;
- `scripts/start_cloud.py` запускает uvicorn без режима перезагрузки Python-кода.

Таким образом, есть доказанный случай нового интерфейса со старым серверным API. Успешный HTTP 200 главной страницы не доказывает актуальность приложения. Это существенный пробел предыдущих проверок запуска, в том числе моих.

## 2. Два пользовательских пути вместо одного

`web/index.html` подключает оба редактора:

| Вход | Интерфейс | Серверный путь | Механика |
|---|---|---|---|
| «Продолжить» у готового приключения (`web/chronicles.js`) | `web/character-creation.js`, страница `#character-creation` | `/api/creation/drafts/{id}/character`, затем `/character/confirm` | `solo/character_creation.py` → `Preparation.launch()` |
| Кнопка героя подготовленного мира (`web/creation.js`) | `web/wizard.js`, модальное окно `#wizard` | `/api/prototype/wizard/contract`, затем `/api/prototype/campaigns` | Native/Nat20 |

Два интерфейса могли бы использовать один общий сервис. Сейчас это разные модели черновиков, проверки и цепочки запуска:

- `solo/character_creation.py:64` явно отвергает уровень, отличный от 1;
- там же самостоятельно считаются ХП и КД (`156–158`), атаки и сложность заклинаний (`174–181`);
- `solo/character_catalog.py` содержит собственные таблицы и публикует `levels=[1]`;
- `CharacterCreationService.confirm()` вызывает старый `Preparation.launch()`, который создаёт обычное состояние кампании;
- `solo/command_backend.py` выбирает Nat20 только при наличии `state['nat20']`, иначе использует `CommandEngine`.

Следствие: успех создания героя через «Продолжить» не является доказательством интеграции Nat20. При приключении пятого уровня такой редактор также принципиально не может собрать требуемого героя. Это не повод отказаться от Nat20, а повод перестать вести основной путь по альтернативной реализации.

## 3. Последняя браузерная приёмка доказывает меньше, чем требуется

В `tests/test_character_editor_ui.py` исходный мир формирует `PreparationFixture`, а браузер обслуживает `PreviewMock` с `offline_mock=True`. Это правильная изоляция для части UI-тестов, но не проверка работоспособности живого облачного Мастера или произвольного PDF.

`tests/test_character_editor_ui.cjs`:

- явно выбирает `PAGE='#character-creation'`, то есть иной редактор, чем модальное окно на прежних скриншотах пользователя;
- действительно собирает героя кликами — эта часть проверки полезна;
- первый ход отправляет через `page.evaluate(fetch(.../command-turn))`, а не через поле чата;
- утверждает только HTTP 200/201, без требования правильного статуса хода, содержательного ответа и подтверждённого изменения состояния;
- в секции «restart» вызывает `page.goto(base)`: сервер не перезапускается; отдельный новый браузерный контекст также там не создаётся;
- число «19 проверок» — внутренние пункты одного сценария, не матрица классов, уровней и отказов.

Поэтому тест может проходить одновременно с неработающим обычным чатом, другим сломанным редактором, старой версией сервера или недоступной облачной генерацией. Это недостаточность приёмки, а не доказательство отсутствия пользы от написанных тестов.

## 4. Продуктовые принципы остаются несовместимыми с частью проверок

В ROADMAP закреплено: неизвестная настройка уточняется, сюжет не является перечнем разрешённых действий. Но в текущем коде:

- `solo/prepared_world.py:1114`: неподтверждённая метаинформация уровня/группы остаётся `essential=True`;
- `solo/prepared_world.py:1579–1581`: разные значения уровней или состава из разных блоков собираются как глобальное противоречие с `essential=True`, без разграничения глав и встреч;
- `solo/first_playable.py:46–51`: универсальный запасной вход требует названного старта, двух мест и дороги;
- `solo/first_playable.py:136–137`: любая существенная ошибка всего результата запрещает рассмотрение универсального входа.

Сохранены также специальные ветви Hoard по хешу и страницам. Они пригодны для конкретного контрольного примера, но не доказывают универсальность обработки книги.

Часть старых защит нужна для целостности механики и источников. Проблема — в смешении вопросов «подтверждён ли факт», «можно ли исполнить действие» и «можно ли вообще начать разговор». Разрешение неизвестного старта в одном модуле не отменяет блокировку метаданных в другом. Отсюда повторение похожих жалоб после локальных исправлений.

## 5. Облако — самостоятельный непроверенный компонент

Журнал текущего профиля в предыдущей диагностике показал `sse_503` для DeepSeek и Gemini, а также успешные ответы Gemini между отказами. Это подтверждает реальные сбои нескольких путей генерации, но не доказывает постоянную недоступность всего API.

`/models` и каталог маршрутов отвечают независимо от генерации. `solo/app.py` для `/probe` использует `mode='connection'`; выбор в `solo/ai_roles.py` ведёт к выбранному рассказчику. Следовательно, одна общая проверка не проверяет все роли. `solo/cloud.py:186` прикрепляет запрос к конкретному endpoint через `provider.only`.

Не следует списывать все проблемы на модель, снимать бюджеты или включать бесконтрольные повторы. Нужны раздельные состояния каталога, конфигурации и последней фактической генерации каждой роли. Живой игровой сеанс нельзя принимать только на моках.

## 6. Нет зафиксированного интегрированного результата

Во время аудита `git status --porcelain` содержит 458 записей путей, включая новые и удалённые; последний коммит — `b881148` от 16 октября. Это не означает, что все изменения плохие. Но нет свежего воспроизводимого контрольного состояния, к которому относятся сразу сервер, интерфейс, ресурсы, схема данных и результаты приёмки.

Последний отчёт редактора сам оставляет три падения создания персонажа в совокупной рабочей копии. Их относят к чужим изменениям и подтверждают сравнением с HEAD. Это полезно для локализации автора изменения, но HEAD от 16 октября не является текущим продуктом. Для пользователя критерий — совместный результат, а не отсутствие регресса в отдельно наложенном патче.

## Почему цикл промптов не помогает

Повторяются пользовательские симптомы, но исправляются разные места исполнения. Большие задания объединяют несколько систем; точечные задания затем запрещают менять соседние системы, на стыках которых и остаётся отказ. Приёмка ориентируется на локальный отчёт, а проверенный результат не переносится в однозначно определённую версию работающего приложения.

Вклад координатора: мои предыдущие промпты тоже расширяли требования раньше закрепления одного пути; при открытии приложения я проверял доступность страницы, но не соответствие загруженного API изменённым файлам. Поэтому ответственность нельзя свести только к DeepSeek.

## Предлагаемый следующий этап

Следующее задание должно быть интеграционным, с одним ответственным за итог, а не очередным расширением списка функций.

1. Зафиксировать текущее совместное состояние исходников и ресурсов, не откатывая чужие правки. Определить актуальные запуск, профиль и версию схемы. Ввести видимую идентичность запущенной сборки/серверного процесса; выпускать интерфейс и API согласованно. Безопасный перезапуск согласовать с завершением/остановкой текущей подготовки, не убивать чужие процессы.
2. Выбрать единственный основной путь персонажа и запуска на Nat20. Все обычные входы должны вести в него. Старую арифметику не развивать и не подменять ею доказательство Native-интеграции. Существующие сохранения сохраняются; их миграция — отдельное явное решение.
3. Довести этот путь в текущей совокупной копии до отсутствия блокирующих падений. Разрешить минимальные изменения смежных модулей, необходимые для этого пути, с ответственностью за интеграцию. Не принимать исключение «это чужой файл» как окончание работы.
4. Зафиксировать короткий критерий: текстовая идея без файла → ручной законный герой → ввод через реальное поле чата → 10–15 последовательных осмысленных действий → сохранение → настоящий перезапуск сервера → продолжение. Проверяются состояние, последствия, отсутствие утечки секретов и сохранность героя, не только HTTP-коды.
5. Тот же путь пройти с одним коротким реальным пользовательским ваншотом, включая требуемый им уровень. Неизвестные настройки уточняются, не закрывают беседу. Факты, предполагаемые сведения и дополнения Мастера различаются. Отдельно подтвердить хотя бы один живой ответ необходимых AI-ролей в разрешённом остатке бюджета.
6. Принять результат пользовательской игровой сессией без помощи разработчика и зафиксировать проверенную версию. Затем расширять охват PDF, вариантов героя, карт, механики и интерфейса. Полная автоматизация D&D и произвольная большая книга не должны быть предварительными условиями первого рабочего сеанса.

Этот план пока не запущен: владелец запросил диагноз. Код, сохранения и работающий сервер оставлены без изменений.
