### Почему обычный вход попадает в старый движок (точное место)

- `solo/command_backend.py:9` — выбор движка: `if 'nat20' in current['state']`.
  Всё решает наличие ключа, а не намерение игрока.
- `solo/preparation.py:203` `launch(...)` (второй редактор) собирает
  `state` вручную: `hero=` модель `Hero`, `ruleset=` пресет,
  `preparation=`..., **но ключа `nat20` не создаёт**.
- `solo/prototype_prepared.py:153` `launch_prepared(...)` создаёт кампанию через
  `Nat20GameEngine.create_experimental_campaign` и `nat20` появляется.
- `solo/prototype_prepared.py:164` прямо запрещает объединение:
  «Черновик связан с legacy-кампанией; она не переводится в Nat20» — это
  единственный такой запрет в коде (проверено по `solo/*.py` и `web/*.js`).

Вывод для выбора решения: соединение двух путей — это не правка одного флага.
`hero` в старом состоянии — модель `Hero` (свой лист), а Native-мир работает с
Nat20-листом (`build`), поэтому «добавить nat20 в state» нельзя: получится
состояние без Nat20-листа, которое движок отвергнет. Правильный единый путь —
вести обычный вход в `launch_prepared`, то есть чтобы подтверждение героя в
обычном интерфейсе собирало Nat20-лист, а не второй `Hero`.

Разделение закреплено тестом `tests/test_character_creation.py:72`
(`test_draft_resume_invalid_confirm_legacy_bypass_and_atomic_idempotent_launch`):
на строках 90–92 он проверяет `state['hero']['ac']==19` и
`state['character_creation']['source']['title']=='SRD 5.1'`, то есть прямо
требует **старую модель `Hero`** как результат подтверждения героя. Перевод
обычного входа в Nat20 значит, что этот тест должен измениться вместе с кодом —
иначе он будет охранять прежний второй движок.

Это изменение затрагивает `solo/preparation.py`, `solo/character_creation.py`,
`web/creation.js` и часть тестов второго редактора. Поэтому оно выполняется
одним связанным шагом с прогоном регресса, а не частичной правкой «наполовину».

### Раунд 10: почему второй редактор нельзя «переключить» на launch_prepared

Проверено опытом, а не рассуждением:

- `launch_prepared` принимает `build: CharacterBuildSpec` из `dnd5e_engine`
  (поля: `species_slug, class_slug, classes, subclass_slug, level,
  ability_scores, equipment, selected_choices, background_slug, hp_mode,
  hp_rolls, ac_calc_mode, attuned_items, ability_score_method`).
- Старый `CharacterDraft` хранит другой набор: `species, class_id, subclass,
  background, method, scores, bonuses, class_skills, species_skills,
  feat_skills, origin_feat, fighting_style, weapon_mastery, kit, ...`.
- Прямое сопоставление упирается в два места: способ характеристик
  (`method` → `ability_score_method`, допустимы только `standard_array` и
  `point_buy`, а старый лист знает больше) и **выборы развития**. Запуск с
  пересчитанным вручную листом падает на
  `ChoiceError: advancement choices still owed: skill x2 at class:fighter level 1;
  skill x1 at species:human level 0; feature x1 at species:human level 0; feature x1
  at class:fighter level 1`.
- Значит вычислить Nat20-лист из старого черновика нельзя: движок сам требует
  выборов, которые старый экран собирал в собственном формате. Любая
  «конвертация с догадками» была бы вторым калькулятором, то есть ровно тем, что
  задание запрещает.

Вывод, меняющий план: правильный единый путь для подготовленного мира — **сам
Native-мастер**, а не переписывание второго редактора. Старый второй редактор
нужен только для черновиков, у которых уже есть старая модель `Hero` (то есть
старых сохранений). Поэтому:
- кнопки нового героя уже ведут в Native (раунд 9);
- `character_creation.confirm` отказывает новому пути (раунд 9);
- 3 красных теста второго редактора — это тесты **устаревшего пути**, и они
  должны быть переписаны на Native-маршрут, а не возвращены в зелёное через
  возврат второго движка.

### Раунд 11: что из этапа B проверяемо без модели

Проверено вызовами, не рассуждением:

### Раунд 12: найден и исправлен дефект «герой заперт в первой сцене»

Проверено текстовыми ходами без модели на Native-кампании из подготовленного мира.

**Что работало сразу:** `walk_intent` (`solo/game.py:287`) распознаёт «иду в
<место>» и исполняет перемещение ДО любого обращения к модели
(`solo/game.py:366-379`). «иду в Доки» → 200 `status=resolved`,
«Прибытие: Доки. Пройдено 0 м за 0 минут.» — настоящий текстовый ход, 0 ₽.

**Дефект:** у мест подготовленного мира стояло `known_to_hero=False`
(значение по умолчанию `WorldLocation`), и Native помечал известным только
стартовое место. А `known()` (`solo/world.py`) требует согласия двух флагов —
`place.known_to_hero` **и** `node.known`. `travel.itinerary()` при неизвестном
месте честно отказывает «Это место ещё неизвестно герою», а известность
появлялась только по прибытии → **замкнутый круг**: выйти из первой сцены
нельзя ни одним путём.

**Правка** в `solo/prototype_prepared.py` (цикл по `package.locations`):

```python
elif not place.secrets:
    place.known_to_hero = True
    for node in package.nodes:
        if node.name == place.name:
            node.known = True
```

Правило: место без секретов — уже опубликованный материал книги, герой знает,
где оно. Место с секретами остаётся неизвестным до игры.

**Результат:** отказ сместился с «место неизвестно» на честный
«Между этими местами ещё не известна дорога. Уточните…» — то есть известность
теперь есть, не хватает только маршрута, которого тестовая книга не задавала.

**Подтверждено с маршрутом в книге** (маршрут добавлен в `geography.routes`,
как его задаёт подготовка книги с дорогами):

```
иду в Пирс   200 resolved -> Пирс  «Прибытие: Пирс. Пройдено 120 м за 4 минут.»
иду в Доки   200 resolved -> Доки  «Прибытие: Доки. Пройдено 120 м за 4 минут.»
```

То есть **осмотр места, перемещение и возвращение работают через обычный
текстовый ход без модели и без денег** — это ровно та часть этапа B
(«перемещение и возвращение при отсутствии препятствий»), которую я раньше
считал недоступной без оплаты. WorldRoute требует `from_/to/meters/minutes/
description` (alias `from`), `known` по умолчанию True.

Отказ модели не ломает сцену: `FALLBACK TEXT: Смолёные сваи уходят в туман.

### Раунд 19: вымысел не может стать фактом мира (память)

### Раунд 47: причина «уточнений» устранена — ход доходит до движка

**Корень найден живым перехватом ответа модели** (скрипт `runtime/ui-tmp/raw2.py`,

```

 "message":"Движок не получил координат... Укажите новые координаты (x, y, z)."}
```

Модель возвращала `status=command` **вместе с непустым `message`**. Валидатор
`solo/game_commands.py` требовал при команде пустой `message` и выбрасывал
`ValueError`, который `solo/game.py:390-391` превращал в общий ответ
«Не удалось однозначно разобрать намерение». Отсюда все прежние `clarification`.

**Исправление** (`solo/game_commands.py`, класс `CommandIntent`): добавлен
`@model_validator(mode='before')` `envelope`, который у настоящей команды с
действием молча отбрасывает сопроводительный текст: действие известно, а
пояснение лишь описывает его. Противоречивые конверты по-прежнему отвергаются.

Проверка правил на пяти случаях:

| Конверт | Итог |
|---|---|
| команда + пояснение | ACCEPT, message='' |
| чистая команда | ACCEPT |
| команда без действия | REJECT 'Command requires one action and no message' |
| уточнение с действием | REJECT 'A non-command requires a message and no action' |
| уточнение без действия | ACCEPT |

`import solo.game_commands` -> IMPORT OK. Сервер перезапущен, health 200.

**Живой ход после правки:** было `clarification` «Не удалось однозначно
разобрать намерение» -> стало `status: rejected`, `narrative: "No active
Nat20 combat"`. То есть намерение теперь разобрано и доходит до движка Nat20,
а отказ приходит от движка по существу (боевой команды вне боя не бывает).

Осталось: подобрать формулировку, которая даёт настоящую команду перемещения,
а не боевую — тогда сессия пойдёт дальше в бой и награду.

### Раунд 69: настоящий баг мастера героя — черновик игрока затирался

значит терял данные клиент, а не сервер и не тест.

`/api/health` вызывает `build_identity()`, а тот запускает
`subprocess.run(['git','rev-parse','--short','HEAD'], ...)` (`solo/build_identity.py:37`).
Процесс `git` наследовал тот же stdin; его поток-читатель навсегда оставался
в `subprocess.py:1599 _readerthread`, `communicate()` не возвращался —
и ответ на health не отправлялся никогда.

**Проверка не на слово.** `solo/app.py:143-147` — `async def health()` вызывал
блокирующий `subprocess.run` прямо в событийном цикле. Это дефект продукта,
а не теста: любой запуск в потоке при чтении stdin вешал бы health.

**Что исправлено в продукте (не костыль в тесте):**
- `solo/build_identity.py:37` — `subprocess.run(..., stdin=subprocess.DEVNULL)`:
  git больше не зависит от stdin хоста.
- `solo/app.py:147` — `identity=await asyncio.to_thread(build_identity)`:
  блокирующий вызов убран с событийного цикла.

**Что исправлено в тесте:** ребёнок закрывает унаследованный stdin и останавливается
по файлу-токену `tmp_path/'stop.token'` (родитель передаёт путь в `sys.argv[3]`);
`Popen(..., stdin=subprocess.DEVNULL)`; проба health читает строку статуса
обычным сокетом, потому что `urllib` уводит loopback-запрос в системный прокси.

**Результат.** `test_pdf_nat20_ui_real.py` — **1 passed (64–78 с)**, повторяемо;
`test_pdf_nat20_ui_real.py` + `test_pdf_nat20_ui.py` — **2 passed (83 с)**.

### Раунд 71: критика и что она изменила

**Мой первый вариант `test_server_restart_real.py` проходил, но доказывал меньше, чем заявлял.**
Критик нашёл четыре ложноположительных пути:
1. Блок повтора был **неотличим от повторного выполнения**: событие перехода не сохраняет
   `game_command`, поэтому `solo/game.py:337-344` на любой повтор отвечает `rejected`
   независимо от идемпотентности. Утверждения «кампания одна / локация та же / версия та же»
   прошли бы, даже если бы ход выполнялся дважды.
2. `history >= history_before` — **пустая проверка**: `history` равен `None`, сравнение `len([]) >= 0`.
3. Ход не проверял **вид события**: ответ модели, не меняющий локацию, прошёл бы так же.
4. Не было доказательства, что ответил **другой процесс**: `process.pid` — это обёртка `.venv`,
   а не сервер. И остановка не обрабатывала таймаут, оставляя процессы жить.

**Кроме того, мои прогоны утекли 12 процессов** (6 пар «обёртка + сервер» с живым
`SOLO_CHILD_PORT` при мёртвых родителях). Я их остановил — осталось 0.

**Переписанный тест закрывает каждый пункт:** ребёнок сообщает свой `os.getpid()`
(≠ родителя, создан позже кампании); перекрёстная таблица-метка пишется отдельным
соединением и читается из кампании ребёнка; родительское хранилище проверяется на неизменность;
проверяется `results[0]['kind'] == 'world_travel'`; повтор проверяется по `rejected`,
нулевому списку событий, **совпадающему дайджесту базы**, неизменным версии/истории/числу кампаний;

### Что работает
- Извлечение текста: 6 документов, 681 страница, 501 244 символа в «Клад королевы драконов».
  Чисто там, где исходный PDF чистый.

  `/api/adventure/review/session` с `confirm_spoilers: true`, cookie живёт 900 с и **держится

### Почему в остальных случаях отказ — три РАЗНЫЕ причины
1. **Обрыв JSON по лимиту вывода.** `output_tokens` упирался ровно в предел:
   1800 → поднял до 4000 → поднял до 8000. С обрывом **сдвинулся и он**: 10 246 → 20 026

   (страница 3906 символов → ответ 20 292 символа, сущность за сущностью).
2. **Схема не передаётся модели.** `structured = json_object` у `interpreter`
   (`solo/cloud.py:170,184-185`): при этом режиме грамматика уходит **текстом в системный
   промпт**, и пределы схемы не обеспечиваются. Отсюда ошибки вида
   `suggestions: List should have at most 30 items …, not 66` и
   `transcription: String should have at most 1600 characters`.
3. **Модель выдумывает цитаты.** `entities.N.name: имя отсутствует в цитате`,
   `entities.N.quote: цитата не подтверждена переданным текстом` — срабатывает на малых
   страницах (8, 109, 110), где обрыва быть не может. Проверка канона
   (`solo/adventure_analysis.py:88,97`) отказала **по делу**: модель дала «The Bell Landing»
   цитатой «The landing has one lit lamp…».

## Раунд 76: три блока SSE 503 в рассказе — причина найдена, и это НЕ зеркала

Владелец прислал три одинаковых блока: «Ошибка внутри SSE: Выбранные зеркала модели
временно недоступны (HTTP 503). Ход не выполнен и не оплачен дважды…».

### Что показала прямая проверка провайдера (RouterAI, без игры)
- Маршрут рассказчика `deepseek/deepseek-v4.1-flash` — **работает**, `200`, в том числе потоком.
- Резервный `cognitivecomputations/dolphin-mistral-24b-venice-edition` — **работает**, `200`, потоком.
- Аналитик PDF `google/gemini-3.8-flash` — вот он и падал, и **не как 503**: провайдер отвечает
  `200`, но внутри потока присылает
  `{"error":{"message":"The request is prohibited due to a violation of provider Terms Of Service.",
  "code":503,"metadata":{"provider_error_code":"403"}}}`.
  То есть настоящий код — **403 (запрет)**, а наружу выставлен **503**.

### Почему сообщение врёт
`solo/cloud.py:73-77`: для кодов 502/503/504 печатается «Выбранные зеркала модели временно
недоступны… выберите другой маршрут в настройках рассказа». Для Gemini это неверно дважды:
(1) это не временная недоступность, а **запрет маршрута по ToS** — повтор через минуту не поможет;
(2) менять маршрут рассказа бессмысленно, потому что падал **анализ PDF**, а не рассказ.

### Деньги
Каждая попытка Gemini списывает ~0,95–1,36 ₽ и заканчивается ошибкой. В журнале **7 подряд**
сбоев 503 (23:36–23:57) плюс `network` через 98,7 с. Эти списания — прямые убытки.

### Вывод
Рассказ не сломан. Сломан **анализ PDF на маршруте Gemini**: маршрут запрещён провайдером,
а интерфейс сообщает об этом как о сбое зеркал рассказа. Нужно: (а) не показывать 503 для
403-ToS и не советовать менять маршрут рассказа; (б) не отправлять повторные попытки на
запрещённый маршрут, чтобы не платить за отказы.
