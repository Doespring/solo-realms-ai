### 1.3 Как движок связан с Solo

Nat20 не имеет durable handle API: **каждая операция переигрывает bounded JSON-рецепт в свежем процессе**, Solo затем коммитит результат своей транзакцией (solo/nat20_api.py:1-17, _worker на :123-139). Это сильное решение — оно само по себе защищает от повторного расхода ресурсов при ретрае.

```
реплика → распознавание намерения → NativeAction (game_commands.py:88)
        → nat20_worker.py → PlayerIntent → dnd5e_engine.orchestrator
        → JSON-ответ → DurableState → транзакция Solo
```

### 1.5 Пробелы — подтверждено кодом

**П1. Пассивные эффекты предметов не применяются.** get_item вызывается в оркестраторе ровно 4 раза, и только для зарядов и разрешения активностей (orchestrator.py:8560, 8616, 11413, 11492). passive_effects читаются только у **способностей** (orchestrator.py:7384). У adamantine-armor ровно один passive-effect, и он меняет лишь флаги Foundry (system.properties, name, img) — механического «крит становится обычным попаданием» нет вовсе. Греп по crit_range|prevent.*crit даёт только auto-crit; обратного механизма не существует.

**П2. Настройка проверяется, но не даёт эффекта.** build_spec.py:656-675 _attuned() валидирует дубли, лимит и принадлежность к equipment и возвращает frozenset. Используется он только в _worn для бонуса доспеха (:701). Прочие эффекты настройки не вычисляются.

**П3. Заряды предметов не восстанавливаются при отдыхе.** В solo/nat20_worker.py:316-321 при отдыхе вызывается только recover_feature_uses — по способностям. recover_item_uses не вызывается ни разу во всём solo.

**П4. use_item объявлен, но не используется.** NativeAction.operation в game_commands.py:90 допускает use_item с полями item_id, activity_id, charges_to_spend. Но в solo строка use_item встречается только в самом контракте и в моке preview_mock.py:38. Живого пути «игрок применил предмет» нет.

**П5. Инвентарь Solo и снаряжение движка — разные миры.** solo/inventory.py (185 строк) содержит 0 упоминаний nat20. equipment в спеку движка берётся из определения кампании (nat20_api.py:105). Купленный в Solo предмет не появляется в бою, и наоборот.

**П6. Ограничение настройки не проверяется по источнику.** attunement_constraint в корпусе заполнен у 22 предметов («by a Wizard», «by a Cleric, Druid, or Paladin» и др.), но _attuned() его не читает вовсе.

### 1.6 Известные дефекты, заявленные самим проектом

solo/nat20_api.py:112-116 перечисляет честный список: hide не тратит действие, у bless неверный бонус к спасброску и дефекты концентрации, rage эмитит отключённый эффект, компоненты заклинаний проверены не полностью. Это заявление кода, его следует сохранить в матрице как есть.

### 1.7 Тесты

В tests/ 173 файла, из них ~28 про Nat20. **Запустить pytest в этой среде не удалось**: песочница DSH отклоняет удаление каталогов, на котором pytest падает в cleanup_dead_symlinks (pytest/tmpdir.py:337). Импорт модулей проверен и работает (solo.nat20_api, solo.inventory_service). Фактическую долю проходящих тестов на этой машине я **не установил** и не выдаю за проверенную.

## 3. Архитектура расширения (минимально инвазивная)

Принцип: **ничего не переписывать**, добавить три тонких шва.

### 3.1 Шов «инвентарь → боец»

Сейчас nat20_api.py:105 берёт equipment из определения кампании. Предлагается вычислять этот список из InventoryEngine Solo на момент боя (надетое + настроенное), не меняя формат кампании. Обратная запись не нужна: Solo остаётся владельцем инвентаря.

### 3.2 Шов «предмет → эффект»

Движок **уже умеет** всё необходимое — ActiveEffect с changes, origin, duration. Не хватает одного: проекции item.passive_effects в активные эффекты бойца при надевании/настройке. Это одна функция в духе orchestrator.py:7380-7391, где сейчас так делается для способностей.

Изменения в движке (фиксировать в PATCHES.json новым патчем, не трогая старый digest):
1. orchestrator.py — проекция предметных passive_effects для надетых/настроенных предметов;
2. activities/attack.py — флаг «криты становятся обычными» (no_crit) для Adamantine-like;
3. rest.py / воркер — вызов recover_item_uses при отдыхе;
4. build_spec.py — проверка attunement_constraint.

Всё остальное — **данные**, а не код.

### 3.3 Шов «русский интерфейс»

Словарь rules_data/i18n/ru/items.json: canonical_id → {name_en, name_ru, synonyms[], explanation}, с пометкой translation_source: "project". Никакого русского текста внутри механики.

## 4. План бестиария

Корпус движка уже содержит **341 монстра**, а извлечённый MONSTERS_AGMM.jsonl — **494 статблока**, но, как верно указано в задании, принадлежность редакции 2024 не доказана. Поэтому:

1. Не сливать 494 в 341 автоматически.
2. Для каждого русского статблока проверить редакцию по маркерам 2024 (новые действия, формулировки КО/БУ/ПО, свойство искусности). Непроверенное — в отдельный слой provisional, недоступный для боя.
3. Стабильный ID — dnd2024.statblock.<slug>, провенанс обязателен (хеш файла, страницы, лицензия).
4. Способность попадает в исполняемый вид только при наличии типизированной активности движка; иначе — статус narrative_only и видимая пометка.

## 7. Риски и ограничения

1. **Запрет AGENTS.md.** Файл AGENTS.md (изм. 23.10.2026 4:26) прямо требует новой команды владельца на разработку. Текущее указание даёт только этапы A–C — код не менялся.
2. **Песочница блокирует pytest** (удаление каталогов). Полный тестовый прогон не подтверждён; нужен профиль вне песочницы.
3. **Число магических предметов расходится**: в движке 296, в извлечении 257. Разница не объяснена и требует сверки — не сливать.
4. **Ручные таблицы**: 6 таблиц внесены вручную (Manual of Golems, Necklace of Prayer Beads, Staff of Power, Staff of the Magi, Wand of Fear, Ring of Shooting Stars) — каждую надо сверить с источником.
5. **Mysterious Deck**: проклятие установлено интерпретацией, а не явной пометкой — не выдавать как свойство.
6. **Патч движка** меняет vendor; нужен новый digest и совместимость сохранений.
7. **Статблоки 2024** — принадлежность редакции не доказана.
