# CONTRACT — что проверено в игре фактически

Сводка к `DELIVERY.md`. Разделы 14.x — хроника проверок; здесь итог: какие игровые действия
подтверждены **механически**, а не совпадением имён в коде.

Проверено в папке движка, `Nat20 0.7.0`, на собственной `.venv`.

## Изменения публичного контракта после итерации 4

Таблица ниже дополняет хронологию §14: всё, что здесь перечислено, меняет то,

**Ловушка, которая уже стоила одного дефекта.** `ChangeMode` в корпусе —
СВОЯ строка (`"override"`, `"add"`, `"upgrade"`), а не номер режима:
константа `_MODE_OVERRIDE` в `rules/character.py` — целое `5`, и сравнение с
ней всегда ложно. Именно на этом `mage-armor` молча не работал до раунда 90.

**Порядок подключения.** SRD (`dnd5e_srd_data`) — всегда; PHB 2024 — только
интегратором из его окружения и никогда в Git; `PATCHES.json` сверяет sha256
файлов движка при `release()`, любая расхождение — отказ, а не предупреждение.

## Что НЕ надо проверять повторно

- `PartyMemberSpec.attack_bonus` и `damage_dice` при `None`/`0` — это незаданные поля, а не
  итог. Движок вычисляет бонус и берёт урон из предмета загрузчика в момент атаки. Итог
  читайте только из событий `attack_rolled` (`roll_total - natural`) и `damage_rolled` (14.95-14.96).

- `encounter_ids` не очищается при смерти врага — так задумано. Признак победы —
  `id in dead_ids` (14.98).

- `end_turn` не является интентом движка. Конец хода — `PlayerIntent(intent_type='pass')`, иначе
  `ValidationError` (14.93).

## Правила чтения событий

| Событие | Поле | Что на самом деле содержит |
|---|---|---|
| `healing_applied` | `amount` | **сырой бросок** (`1d10 + уровень`) ДО ограничения максимумом HP. Вылечено = `hp_after - hp_before`. При HP 11/12 сид 6 даёт `amount=11`, а фактически +1 (14.115) |
| `attack_rolled` | `roll_total - natural` | модификатор атаки (+5 у бойца 1 ур.) (14.96) |

## Награда: когда опыт НЕ молчит

Нулевой опыт обрабатывается явно, а не теряется (`nat20_worker.py:434-451`):

- `reward.kind == 'printed_experience'` — берётся `reward.experience`, `xp_value` врага не нужен;
- обычная награда — `reward` = квитанция с `experience`, состояние `experience` растёт;
- `amount == 0` — ставится `reward_pending` с причиной «Награда книги не оценена в текущих данных».

Требование «проставить `xp_value`» (14.99) относится только к наградам по нативному опыту
столкновения (`reward.kind = 'native_encounter_xp'`), а не ко всем кампаниям.

## Идентификаторы в бою

Актёр кампании `road-raider` в бою становится `goblin` (`nat20_worker.py:343`). Атака по
`road-raider` даст `Unknown or non-hostile target`; по `goblin` — работает.

## Обязательные поля, которые легко забыть

| Поле | Где | Без него |
|---|---|---|
| `weapon_id` | `PlayerIntent(intent_type='attack')` напрямую | молчаливый no-op (14.97) |
| `xp_value > 0` | запись актёра в кампании | победа без опыта, `xp_awarded={}` молча (14.99) |
| `attuned_items` | сборка персонажа | предметы настройки не дают бонуса; в проде запрещён и валидатором кампании, и отсутствием предметов (14.87, 14.113) |
| `initiative` | `EncounterMemberSpec` | ошибка валидации |

## Загрузчик: главное отличие прода от корпуса

`solo/nat20_content.py:182` создаёт **`MemoryAssetLoader`** (не `BundledAssetLoader`). Состав в игре:

```
items:    3  -> ['chain-mail', 'longsword', 'shield']   (у всех uses = None)
spells:   0  -> []
monsters: 1  -> ['goblin-warrior']
```

Всё, что проверено через `get_lib_loader()` (546 предметов корпуса), в игре может быть недоступно.
Магические предметы и заряды перепроверять только через `release()` (14.113, 14.114).

## Событие восстановления зарядов (14.203)

**Движок оценивает ОДНО событие. Длительный отдых не влечёт рассвет.**

`periods_covered` — тождество: событие срабатывает только на своё правило.

| Событие | Кто решает, что оно наступило | Что восстанавливает |
|---|---|---|
| `"sr"` | хост: короткий отдых завершён | пулы с правилом `sr` |
| `"lr"` | хост: длительный отдых завершён | пулы с правилом `lr` |
| `"dawn"` | хост: игровые часы прошли рассвет | пулы с правилом `dawn` |
| `"day"` | хост: сменились игровые сутки | пулы с правилом `day` |
| `"dusk"` | хост: наступили сумерки | пулы с правилом `dusk` |

Вызов: `recover_item_and_activity_pools(counters, event, equipment, loader, rng=...)`.
`rng` обязателен для формул (`1d6 + 1`) и должен быть воспроизводим при replay.

**Отдых через рассвет — два события:** `"lr"`, затем `"dawn"` (и `"day"`, если сутки
сменились). Одно `"lr"` их не заменяет.

**Обязанности хоста (движок часы не читает и SQLite не знает):**

1. Хранить игровое время и определять наступление рассвета и смены суток.
2. Обрабатывать каждое событие РОВНО ОДИН РАЗ: хранить id последнего обработанного
   события каждого вида. Повторная передача добавит заряды — защита на хосте.
3. Сохранять seed вместе с id события, иначе replay даст другие числа.
4. Не передавать `"dawn"` из-за одного только `"lr"`.

Проверено исполнением: `lr` оставляет dawn-пул (5 -> 5), `dawn` без отдыха
восстанавливает (5 -> 1), расходник без `recovery` не восстанавливается, replay
детерминирован. Тесты: `test_a_long_rest_does_not_imply_dawn`,
`test_one_call_restores_every_pool_the_kit_owns`.
## Границы: что здесь НЕ проверялось

- Правка `solo/` (патч зарядов, `attuned_items`) — файлы принадлежат основному потоку.
- Схема кампании основной папки.
- Три отчёта `playable-*.xml`: генератора в коде нет (14.91). **При этом `capabilities.json:172-180`**
  **объявляет `verification: behaviorally_verified` и ссылается на эти отчёты.** Это расхождение;
  интегратору не следует считать `behaviorally_verified` доказанным запуском — отчёты лежат файлами
  (`integration/nat20/reports/`), но воспроизвести их в этой папке нельзя: `test_nat20_playable_rules`
  структурно невыполним (см. `KNOWN_TEST_FAILURES.md`).
- Приёмка полного пользовательского пути — за интегратором.
