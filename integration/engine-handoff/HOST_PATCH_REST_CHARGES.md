# Патч хоста: восстановление зарядов предметов и пулов активностей

Статус: **спецификация для интегратора**. Файл `solo/nat20_worker.py` принадлежит общему
чату; этот поток его не правит (AGENTS.md: host/adapter меняет интегратор).

## СЕМАНТИКА ВОССТАНОВЛЕНИЯ — ИСПРАВЛЕНО В 14.203

**Правило:** движок оценивает ОДНО событие, которое ему сообщили. Длительный отдых НЕ влечёт рассвет.

`periods_covered` теперь тождество:

```
periods_covered("sr")   -> ("sr",)
periods_covered("lr")   -> ("lr",)          было ("lr", "dawn", "day")
periods_covered("dawn") -> ("dawn",)
periods_covered("day")  -> ("day",)
periods_covered("dusk") -> ("dusk",)
```

### Какие события передаёт хост

| Событие | Когда | Что восстанавливает |
|---|---|---|
| `"sr"` | короткий отдых завершён | только пулы с правилом `sr` |
| `"lr"` | длительный отдых завершён | только пулы с правилом `lr` |
| `"dawn"` | игровые часы прошли рассвет | пулы с правилом `dawn` |
| `"day"` | сменились игровые сутки | пулы с правилом `day` |
| `"dusk"` | наступили сумерки | пулы с правилом `dusk` (напр. `robe-of-stars`) |

**Отдых через рассвет — это ДВА события**, и хост обязан передать оба, если игровое время
действительно прошло рассвет: сначала `"lr"`, затем `"dawn"` (и `"day"`, если сутки сменились).
Одно `"lr"` их не заменяет.

### Проверено исполнением (корпус, `BundledAssetLoader`)

```
1. lr без рассвета, жезл (dawn):        spent 5 -> 5     НЕ восстановлен
1b. sr, жезл:                            spent 5 -> 5
2. dawn без отдыха, жезл:                spent 5 -> 1     восстановлен
2b. day при dawn-пуле:                   spent 5 -> 5     это не рассвет
4. sr при lr-пуле (brass-horn, day):     spent 5 -> 5
4b. day-событие (brass-horn):            spent 5 -> 4     по своему правилу
5. расходник acid (без recovery):        spent 1 -> 1     не восстанавливается
6. replay dawn, seed 11, дважды:         результаты равны (0 == 0)
3. повторная обработка результата:       не больше исходного (0 <= 0)
```

### Требования к сохранению событий (обязанность хоста)

1. **Источник времени.** Игровое время, наступление рассвета/смены суток — в сохранённом
   состоянии хоста. Движок не читает ни системные часы, ни SQLite.
2. **Обработка ровно один раз.** Хост хранит идентификатор последнего обработанного события
   каждого вида (например `last_dawn_epoch`, `last_day_index`, `last_rest_id`) и передаёт
   событие только при его смене. Повторная передача того же события не должна добавлять заряды:
   движок формулу к уже восстановленному пулу применит снова, поэтому защита — на хосте.
3. **Воспроизводимость.** Формулы `1d6 + 1` и подобные зависят от `rng`. Хост обязан сохранять
   seed события вместе с его идентификатором, иначе replay даст другое число зарядов.
4. **Порядок при отдыхе через рассвет:** `lr` -> `dawn` -> (`day`). Каждое событие — отдельный
   вызов с отдельным seed.
5. **Чего не делать:** не передавать `"dawn"` только потому, что был `"lr"`. Не вычислять
   «наступил ли рассвет» внутри движка.


## Проверка механизма (исполняемый скрипт)

Запустить перед подключением патча. Не требует обвязки приложения.

```python
import random
from dnd5e_engine.lib_loader import BundledAssetLoader   # НЕ get_lib_loader()!
from dnd5e_engine import recover_item_uses

corpus = BundledAssetLoader()
it = corpus.get_item('wand-of-magic-missiles')
assert it is not None, 'предмет не найден в корпусе'
assert it.uses.max == '7', it.uses.max
assert [r.period for r in it.uses.recovery] == ['dawn']

rules = {'wand-of-magic-missiles': it.uses.recovery}
c = {'item_use:wand-of-magic-missiles': {'spent': 7}}

dawn = recover_item_uses(dict(c), 'dawn', rules, rng=random.Random(1))
lr = recover_item_uses(dict(c), 'lr', rules, rng=random.Random(1))
sr = recover_item_uses(dict(c), 'sr', rules, rng=random.Random(1))
assert dawn['wand-of-magic-missiles'] < 7, 'рассвет должен восстановить'
assert lr['wand-of-magic-missiles'] == 7, 'отдых сам по себе не рассвет (14.203)'
assert sr['wand-of-magic-missiles'] == 7, 'sr не должен трогать'
print('ok: dawn ->', dawn, '| lr ->', lr, '| sr ->', sr)
```

Ожидаемый вывод: `ok: dawn -> {'wand-of-magic-missiles': 4} | lr -> {'wand-of-magic-missiles': 7} | sr -> {'wand-of-magic-missiles': 7}`

**Внимание (14.203).** До исправления `periods_covered` скрипт проверял `lr` и давал 4. Теперь
длительный отдых dawn-пул НЕ восстанавливает — восстанавливает событие `dawn`.

**Почему `BundledAssetLoader()`, а не загрузчик из `release()`:** `release()` возвращает
`MemoryAssetLoader` с прод-набором (3 предмета), и жезла там нет. Глобальный `get_lib_loader()`
при этом НЕ меняется и видит весь корпус (14.148 опровергнуто в 14.167). Это два разных набора,
а не порча состояния.

Трата заряда боевым интентом проверена отдельно (14.149): `use_item` -> `spent` 0 -> 1.

## Почему разница между пулами важна

`activityUses` — пул свойства, а не предмета (SRD 5.2: «Once one of these properties is used,
it can't be used again until the next dawn»). У `ivory-goats` три свойства с пулами 15/7/30
и у каждого свой период. Поэтому восстановление идёт по правилам САМОЙ активности, а ключ
содержит и предмет, и активность.

## Что должен сделать интегратор

Рядом с существующим блоком `recover_feature_uses`, после него. **Один вызов делает всё:** правила предметов и их свойств функция читает сама, периоды `dawn`/`day` подхватывает через `periods_covered`, ключи возвращает готовыми.

```python
from dnd5e_engine import recover_item_and_activity_pools

period = "sr" if action.kind == "short_rest" else "lr"
counters = hero.get("custom_counters")
if counters is None:
    counters = hero["custom_counters"] = {}
# ВНИМАНИЕ: это только надетое при создании персонажа (build.equipment).
# Поля hero["items"] НЕ существует (PartyMemberSpec: 49 полей, есть equipment и
# attuned_items, поля items нет). Предметы, выданные позже и лежащие в рюкзаке,
# в hero отсутствуют вовсе — их заряды этим кодом НЕ восстановятся.
slugs = tuple(sorted(s for s in (hero.get("equipment") or ()) if s))

    counters, period, slugs, loader, rng=rng,

    counters[key] = {"spent": spent}
```

> `hero["equipment"]` содержит только надетое при создании персонажа. Предметы из рюкзака
> в `hero` отсутствуют вовсе, поэтому их заряды этим патчем не восстановятся. Для полного
> покрытия интегратору нужно отображение UUID из `solo/inventory.py` в слаг движка.

## Загрузчик

`loader` приходит из `solo/nat20_content.py:release()`, который создаёт **`MemoryAssetLoader`** — строка 182: `loader = MemoryAssetLoader(**documents)` — и до возврата падает с `ValueError` при любом несовпадении версии или pin. У этого класса есть `get_item` (проверено: `type(L).__name__ == 'MemoryAssetLoader'`).

**Исправление прежней редакции.** Здесь было написано `BundledAssetLoader` (строка 46) — это неверно: `BundledAssetLoader` живёт в другой функции (`weapons()`) и до отдыха не доходит.

**Состав загрузчика в текущей комплектации** (проверено исполнением `release()`):

```
items:    3  -> ['chain-mail', 'longsword', 'shield']   (у всех uses = None)
spells:   0  -> []
monsters: 1  -> ['goblin-warrior']
```

**Следствие: патч в текущей комплектации не проявится.** Ни у одного предмета нет поля `uses`, поэтому счётчики с ключами `item_use:`/`activity_use:` не возникают и восстанавливать нечего. Логика патча корректна и понадобится, когда в комплектацию войдут предметы с зарядами.

`loader=None` в этом пути недостижим. Но если интегратор решит звать блок из другого места, где загрузчик не гарантирован, дешёвая защита:

```python

    for key, spent in recover_item_and_activity_pools(...).items():
        counters[key] = {"spent": spent}
```

Без неё на загрузчике без `get_item` первый же отдых даст `AttributeError` — молчаливо это не пройдёт, но лучше не ронять отдых.

## Период восстановления: `dawn` не приходит из отдыха

`recover_item_uses` и `recover_activity_uses` принимают `period` (`"sr"` / `"lr"` / `"dawn"`).
У `wand-of-magic-missiles` восстановление `dawn` с формулой `1d6 + 1`; у бусин
`necklace-of-prayer-beads` — `dawn/recoverAll`. Хост же при отдыхе передаёт только
`"sr"` / `"lr"`, поэтому вызов в рецепте ниже проходит их БЕЗ учёта `dawn`-правил.

Правильное решение принимает интегратор, вариантов два:

**РЕШЕНО в 14.203 — по смыслу это прежний вариант 2.** Движок НЕ считает, что длительный отдых
влечёт рассвет. `periods_covered` — тождество: событие срабатывает только на своё правило.
Хост передаёт `"dawn"`/`"day"`/`"dusk"` тогда и только тогда, когда игровое время дошло до них.

Оба прежних варианта ОТМЕНЕНЫ, не выбирайте их:

1. ~~Длинный отдых восстанавливает и `dawn`-пулы~~ — так движок работал до 14.203
   (`periods_covered("lr") == ("lr", "dawn", "day")`). Отменено: это допущение хоста
   внутри движка; отдых не доказывает наступление рассвета.
2. ~~Отдых — источник `dawn`, только когда завершается на рассвете~~ — по смыслу верно,
   но «завершился на рассвете» решает ХОСТ. Реализовано именно так: отдельное событие.

Проверено запуском (14.203):

```python
recover_item_and_activity_pools(counters, "lr", items, loader, rng=Random(7))
# жезл магических снарядов (dawn): 5 -> 5    НЕ восстановлен
# ожерелье молитвенных бус (dawn):  1 -> 1    НЕ восстановлен
# козлы из слоновой кости (day):    15 -> 15  НЕ восстановлены

recover_item_and_activity_pools(counters, "dawn", items, loader, rng=Random(7))
# жезл: 5 -> 1     ожерелье: 1 -> 0     козлы (day): 15 -> 15
```

**Ключи активностей нельзя угадать — их надо взять из данных.** Счётчик активности в `counters`
называется `activity_use:<предмет>::<id активности>`, где `id` — случайная строка из корпуса,
а не читаемое имя:

```python
# правильно: id берётся из самой активности
for item in items_docs:
    for act in item.activities:
        key = f"activity_use:{item.slug}::{act.id}"
        counters[key] = {"spent": 1}
```

**Тихий отказ.** Если передать угаданный ключ вида `activity_use:necklace-of-prayer-beads::bead`,
функция НЕ выдаст ошибку — она вернёт исходное значение `1` и `15`. Пул просто не будет найден, а
результат будет выглядеть правдоподобно. Это главная ловушка интеграции: «не восстановилось» будет
означать ошибку в ключе, а не в движке.

Реальные id в корпусе этой версии: ожерелье молитвенных бус — `SEwmmaZFABa5L61F`, козлы из слоновой
кости — `hDc2bhCP7qL52Z1J`. Они случайны и могут измениться при обновлении корпуса — брать из данных,
а не хардкодить.

Пункты 1 и 2 выше — исторические варианты, которые интегратору выбирать НЕ нужно:
достаточно передавать `"sr"`/`"lr"`, как в рецепте. Единственное исключение —
`robe-of-stars`: его период `dusk`, который долгий отдых не накрывает (сумерки от сна
не наступают). Если нужно восстановить и его, передайте `"dusk"` отдельным событием.


### Предметы с периодом `dusk`: что делать хосту

Долгий отдых **не накрывает ни один календарный период** — ни `dawn`, ни `day`, ни `dusk` (14.203).
Календарные события передаёт хост отдельным вызовом.
В корпусе есть ровно один предмет с периодом `dusk`: `robe-of-stars`
(«Одеяние звёзд»). Проверено по всем периодам:

| period | 6 зарядов превращаются в |
|---|---|
| `sr`, `lr`, `dawn`, `day` | 6 (не восстанавливает) |
| `dusk` | **2** (при seed 0; бросок `1d6` даёт 2..6) |

Поэтому рецепт выше, передающий только `"sr"`/`"lr"`, оставляет этот предмет
невосстановленным навсегда. Это не дефект — правило требует именно сумерек.

**Что делает хост.** Если у вас в игре есть смена суток (утро/вечер), передайте
`"dusk"` отдельным вызовом в момент перехода:

```python
if world_clock.just_became_evening():
    for key, spent in recover_item_and_activity_pools(
        dict(hero.get("custom_counters", {})), "dusk", equipped, loader
    ).items():
        hero["custom_counters"][key] = {"spent": spent}
```

Если смены суток в игре нет, предмет остаётся с израсходованными зарядами — это
честное поведение, а не забытый случай. Альтернатива (считать вечер частью долгого
отдыха) — домысел, в правилах такого правила нет.
## ИСПРАВЛЕНО в 1411053: почему раньше патч восстанавливал НОЛЬ

В первой версии этого документа рецепт передавал в движок ровно тот период, который пришёл от хоста: `"sr"` или `"lr"`. А весь корпус предметов заряжается на `dawn` или `day`:

| Предмет | Период правил | `sr` | `lr` | событие `dawn` | событие `day` |
|---|---|---|---|---|---|
| `wand-of-magic-missiles` | `dawn` | 5 -> 5 | 5 -> 5 | **5 -> 1** | 5 -> 5 |
| `necklace-of-prayer-beads` | `dawn`, `recoverAll` | 1 -> 1 | 1 -> 1 | **1 -> 0** | 1 -> 1 |
| `ivory-goats` (три свойства) | `day` | 15 -> 15 | 15 -> 15 | 15 -> 15 | **15 -> 14** |

**Таблица обновлена в 14.203.** Прежний столбец «`lr` (сейчас)» показывал 5->1 / 1->0 / 15->14 —
это поведение ОТМЕНЕНО: длительный отдых не влечёт рассвет.

Патч, применённый буквально, не менял НИЧЕГО, и по критерию из раздела «Проверка» интегратор заключил бы, что он не работает. Причина была в движке: `_recover_uses` сравнивал `r.period == period` строго, и `lr` не совпадал ни с `dawn`, ни с `day`. Коммит `1411053` добавил `periods_covered`:

```python
periods_covered("lr")  # -> ("lr", "dawn", "day")
periods_covered("sr")  # -> ("sr",)
```

Обоснование по SRD 5.2: долгий отдых — это ночь, после которой рассвет наступил и день сменился. Короткий отдых до рассвета не дотягивает. Искусственное `dawn`-событие интегратору добавлять НЕ нужно: достаточно передавать `"sr"`/`"lr"`, как сейчас.
## Ловушка: recovery=None восстанавливает ВСЁ

> **Внимание (14.71).** Этот раздел относится к НИЗКОУРОВНЕВОЙ `recover_item_uses(...)`.
> Рецепт выше вызывает `recover_item_and_activity_pools(counters, period, equipment, loader, rng=...)`,
> у которой параметра `recovery` НЕТ вовсе — попасть в ловушку, копируя рецепт, нельзя.


`recover_item_uses(counters, period)` без явной таблицы восстанавливает каждый счётчик `item_use:` в 0 на любом отдыхе. Именно поэтому таблицу передавать ОБЯЗАТЕЛЬНО: иначе одноразовые предметы (`comet`, `auto_destroy: True`, `recovery: []`) станут бесконечными. Проверено:

```python
recover_item_uses({"item_use:comet": {"spent": 1}}, "dawn", None)        # -> {"comet": 0}  ОШИБКА игрока
recover_item_uses({"item_use:comet": {"spent": 1}}, "dawn", {"comet": []}) # -> {"comet": 1}  верно
```

Правило внутри `_recover_uses` (`rest.py:288-298`): `recovery is None` -> `spent = 0`; таблица есть, но для этого периода правила нет -> счётчик СОХРАНЯЕТСЯ.

**Практический вывод:** в таблицу надо класть КАЖДЫЙ предмет из `hero["equipment"]`, у которого есть пул, даже если `uses.recovery` пустой. Пример кода выше это делает, но если написать `if item.uses.recovery:` вместо `if item.uses is not None:` — одноразовые предметы станут бессмертными. Таблица `item_recovery` обязана содержать ключ со значением `[]` для consumables, а не отсутствовать.

## Проверка, что патч сработал

> **Невыполнимо в текущей комплектации.** Ниже требуются `wand-of-magic-missiles` и `necklace-of-prayer-beads`, но в загрузчике `release()` их нет (`get_item` = None). Все числа этого раздела получены на загрузчике корпуса (`get_lib_loader()`, 546 предметов), а не на прод-загрузчике. Чек-лист применим после расширения комплектации.

> **Исправлено (14.70).** Шаг 2 нельзя выполнить через `period='dawn'`: хост
> (`solo/nat20_worker.py:319`) передаёт только `'sr'` или `'lr'`. Период `dawn` появляется
> лишь как покрытие ВНУТРИ `lr` (`periods_covered('lr') == ('lr','dawn','day')`).
> Используйте длинный отдых — он даёт тот же результат (проверено: `dawn` и `lr` совпали).

1. Взять `wand-of-magic-missiles` (пул предмета 7, `dawn`, `1d6 + 1`) и
   `necklace-of-prayer-beads` (пула предмета нет; у бусин свой пул `1`, `dawn/recoverAll`).
2. Использовать оба, закончить бой, выполнить **длинный отдых** (`period='lr'`) с `rng`.
3. Ожидание (сравнивать НЕРАВЕНСТВОМ, не с константой):
   `item_use:wand-of-magic-missiles` было 5 -> стало в диапазоне 0..3 и МЕНЬШЕ 5
   (правило `1d6 + 1` бросает кубик: остаток = max(0, 5 - бросок));
   `activity_use:necklace-of-prayer-beads::<bead>` было 1 -> стало ровно 0
   (правило `recoverAll` кубик не бросает, результат детерминирован).
4. Без патча оба счётчика остаются как были — проверяется ПО СОСТОЯНИЮ
   `state['hero']['custom_counters']` (пишется в `solo/nat20_worker.py:210`):
   до патча там 5 и 1, после — меньше 5 и 0.

> **Не ждите конкретного числа (14.74).** Ожидание «после — 1 и 0» верно только при
> seed 7. Прогон: seed 0 -> 0, seed 1 -> 2, seed 2 -> 3, seed 3 -> 2, seed 7 -> 1.
> Все эти значения верны. Если сверить с константой 1, рабочий патч покажется сломанным.

5. Отрицательный контроль: `comet` (`recovery: []`) после отдыха НЕ восстанавливается;
   короткий отдых (`'sr'`) не меняет ни один счётчик — это признак отсутствия патча.

## Ограничение

Движок не имеет собственного API «отдых»: `resolve_long_rest`/`resolve_short_rest`
считают HP, кости хитов и ячейки, а счётчики восстанавливает вызывающая сторона через
`recover_*`. Поэтому дефект — в хосте, а не в движке; со стороны движка контракт
задокументирован и покрыт тестом `test_activity_pools_recharge_on_their_own_rules`.
